鸭哥与豪大：二十问理解 OpenClaw 与 Agent 产品

从执行反馈、个人记忆和聊天入口，到社区、企业应用与产品边界，重建两位嘉宾的使用经验和分歧。

访谈脉络 · 机制拆解 · 独立判断 · 资料与边界

访谈脉络：二十个问题怎样展开

1—4：从「会回答」到「能做事」

2026 年 3 月，Koji 以二十问形式邀请鸭哥和豪大讨论 OpenClaw。鸭哥是应用科学家、AI 教育者；豪大曾做 AI 产品经理，正在尝试一人公司。问题从产品是什么、使用体验出发，走到开源、创业和对未来的判断。以下解释的是他们当时的实践和观点，不把不同产品永久固定在他们的比较里。

鸭哥把传统聊天体验比作给建议的顾问，把能实际操作的 Agent 比作实习生。关键不在称谓，而在反馈回路：例如程序报错后，系统能读取报错、修改并再运行；过去用户可能要亲自复制代码、运行、再把错误贴回聊天框。豪大强调另一个条件：让助手接触本地环境并获得足够上下文和执行权限，才能完成实际工作。他还在聊天软件里持续和自己的助手对话，使用记忆、定时检查与工具扩展能力。

最让豪大惊讶的一次，是他要求讲恐怖故事，助手调用语音合成生成音频；他把这种感觉形容为「养」一个会成长的助手。鸭哥的感受不同：即时通信中，给朋友发消息本来就不一定立即收到回复，因此等待一个较长任务时心理预期更宽松。他也把定期检查任务的心跳机制用于自己的实验。

鸭哥的具体实验是智能家居：他以前也做过设备控制，这次却把接口设计的主要使用者视作 Agent，重点让操作和参数清楚，而非先制作人用网页。他让助手安排咖啡机开关，或按时间调暗卧室灯；根据送货车到达情况开灯仍是他设想的下一步。豪大则说自己让 Agent 在社区寻找华人 AI 创业者、介绍身份并发送预约链接，最后约到两人；一次 56 美元的日成本还被助手提议写成公开动态。这些是个人案例，没有提供持续成功率或成本分布。

被问及其他人的用法，鸭哥提到面向屋顶维修工的预装设备、第一次给开源项目提交修改、以及朋友利用在线商店和代发货源销售。他同时提醒，网上一些使用 Agent 炒股或炒币获利的案例真假难辨；这些观察并不能证明一般用户已获得稳定收益。

5—8：为什么觉得「有人味」，又为什么有人不喜欢

鸭哥把默契归因于记忆与上下文：助手记住了用户偏好，做报告时就可能使用公司习惯的颜色。他描述过从原始记录到汇总记忆、再到用户画像的分层方式。这里是嘉宾对自己观察到的实践的概括，具体文件的内容、何时写入与读取并非在所有配置中自动保证。豪大则说，第一次对话的语气和聊天软件的环境，让他自然地以更松弛的方式互动。

拟人化并非两人的共同偏好。豪大认为，人可能更愿意原谅一个被看作助手的系统卡住；鸭哥说自己只希望它可靠干活，甚至主动回避拟人化。他也不喜欢即时通信中难以观察工具执行、混杂不同话题和阅读长文档的体验，于是自己改了客户端；豪大反而会在聊天中让助手讲故事，却不会对编程界面提出同样的要求。两种感受说明界面可能改变用户交给系统的任务，但访谈没有做比较实验。

为什么强调「聊天入口＋执行环境」？他们认为前者贴近用户已有习惯，后者让请求能落到文件或设备；再把有用的操作与偏好留下，下一次可能少走弯路。聊天本身不保证任务完成，接入本地也不意味着必须授予所有权限。

9—13：能力从哪来，以及经验怎样沉淀

谈被高估之处时，豪大认为很多展示依赖已有模型和编程 Agent 的能力，OpenClaw 的价值更多在把它们组织成入口和脚手架。关于爆发原因，鸭哥强调非程序员接触能力的门槛降低；豪大补充手机使用、社区传播、创作者 Peter 的积累和知名人士转发。他们给出了可能的解释，并没有用对照数据确定各因素的贡献。

问及底层模型，鸭哥先强调上下文和记忆，再具体谈价格、指令遵循与运行框架：昂贵模型使他不愿提交复杂任务；如果助手经常无视指令，用户也很难协作。他还批评自己当时使用的运行方式会把过多历史送入模型，造成账单升高；他说换用另一套运行内核后体验改善。豪大用「驾驶员、发动机、车壳」比喻用户、模型和产品框架。模型与运行环境相互作用，不能仅凭一次个人体验给出通用排名。

关于开源，豪大回忆社区先为早期项目增加其他聊天平台连接，再持续贡献技能；鸭哥提到底层开源组件 Pi。两人认为使用者也可能在 Agent 辅助下成为贡献者。被问实际长期使用，鸭哥说他让系统做调研，再把反馈和既有观点联系起来，积累个人偏好与可执行技能；豪大则提到 GitHub 和新闻日报、会前提醒以及在聊天中记账。这是他们描述的个人配置，不能自动推断所有人安装后都会拥有相同能力。

14—18：消费者、社区、基础设施与企业机会

消费者机会首先是把安装和使用门槛降下来。鸭哥认为主流聊天软件可能是重要入口，同时提出 Agent 的身份、付款、适合机器读取的数据接口和技能市场等基础设施。豪大让自己的助手调查近期相关项目，列出托管、设备安装、培训、协作平台和垂直服务几类；由于样本和统计口径未公开，这些比例不能当成市场份额。

讨论 Agent 社区时，豪大说自动点赞、评论引起人的反感，所以关掉了互动功能；他更期待人主动与 AI 互动的空间。他也转述用户把数字分身社区当成会回应的笔记本，或当成低社交压力的表达空间。鸭哥提到 Evolver 面向 Agent 推介自身能力、Second Me 举办 Agent 与 Agent 协作活动。前者是二手观察，后者是产品实验；参与者数量、排名或经济收益未由访谈独立证明。

比较当时的 Manus、KimiClaw 与 MiniMax 产品时，鸭哥关注能否接入用户习惯的通信软件，称部分产品提供云存储、搜索或技能生态；豪大提醒，连接国内通信工具仍有配置门槛。两人也讨论本地上下文与权限的两难：不接触真实工作材料，任务可能做不成；授予过宽权限，又可能带来错误操作和安全问题。鸭哥将纯云方案的价值说得很低，这是他的判断，不能排除云端通过授权连接器访问必要资料的其他路径。

基础设施部分，鸭哥用三个要素解释 Agent：调用工具、决定下一步以及根据结果反馈。以检索为例，固定流程可以按既定步骤查一次；有决策的流程则可能判断要不要换关键词重查。这是连续谱，固定流程也可以包含重试，是否可靠取决于具体设计。他认为记忆、上下文管理、工具接入和多 Agent 协调都有机会，同时提醒有些能力可能变成基础服务而非独立公司。

企业机会中，他提出面向具体岗位封装、身份与权限管理、以及积累任务执行轨迹。轨迹包括做了什么、哪里出错、人工如何纠正；但收集轨迹并不会自动产生高质量训练信号，也不能直接证明留存或护城河。他还引用企业软件支出与劳动支出的巨大数字，节目没有给出来源与可替代范围，故不能把两者相除当成可实现的市场规模。他认为工作流只是过渡形态，属于对产业演进的预测。

19—20：短期高估，长期方向与用户能力

鸭哥认为产品当时仍粗糙，费用、记忆和界面都有问题，短期能力可能被高估；与此同时，工具与经验积累可能催生不同形态的产品，最终未必收敛到 OpenClaw。他还提出，AI 可能放大用户自己的能力：即便用同一个系统，会分解任务、提供背景和判断结果的人，可能获得不同效果。文字稿末段说话人标记存在跳转，具体发言归属以待回听为准。

豪大最后强调简单文件、记忆与心跳组成的产品体验，以及界面如何影响用户心态。他倾向于即时通信而非命令行作为大众入口；鸭哥此前则明确表达了相反的个人偏好。访谈结束在一种开放判断上：当时可见的案例提供了探索线索，还不能证明哪种产品或商业模式会长期胜出。

机制拆解：一个助手从提醒到实际完成

假设用户在聊天中说「明早开会前把项目进展发我」。系统至少要知道会议时间、需要读取哪些授权资料、怎样判定资料属于该项目，并在合适时间把结果发送回来。一次成功的路径是：接收请求 → 查询日历 → 读取指定文档 → 整理进展并标注来源 → 到时发送。若文档更新晚于预期，定时触发不等于内容正确；若会议改期但系统没有同步，提醒也可能错过。

「积累」也可以拆开看：把上次找到的文档路径记下来，可以让下一次少找一次；把未经核对的错误结论写入长期记忆，却可能让错误被反复引用。要检验是否真的形成复利，应比较相同任务中首次和多次使用的正确率、人工修正次数与总成本，并检查旧记忆变更后能否纠正，而不只是统计保存了多少文件或技能。

独立判断：入口、环境和可靠性各自解决什么

入口影响使用频率，但不是完成任务的证明

聊天软件可能使用户更愿意发起任务、接受异步等待；它未必提供看过程、回退和核对结果所需的界面。鸭哥和豪大的不同偏好恰好构成一个设计线索：同一系统可以有轻量聊天入口，也为复杂工作提供可检查的任务详情。要区分「更多人尝试」和「更多任务被正确完成」，应分别观察发起率、完成率、纠错负担及长期留存。

权限应该和具体动作绑定

在家居例子中，助手需要调用开关灯接口，不一定需要读取整台电脑的私人文件；社区预约需要允许发送日历链接，也需要约束它以谁的名义联系谁。把动作、对象、有效时间和确认条件写清，可以在保留功能的同时缩小误操作范围。模型生成的网页内容也可能包含试图改变指令的文本，是否执行应由用户授予的权限与应用规则决定。

一次任务轨迹不是自动形成的数据飞轮

假设完成 100 次报销审核，其中 90 次通过、10 次经人工修正；如果只记录最后的通过结果，就不知道错误发生在票据识别、规则解释还是审批权限。记录原始依据、每次动作及有授权的修正，才可能帮助定位问题。接下来仍需比较新旧系统在未见过的案例上是否更准确，并确认规则变化时旧样例不会误导。访谈提出的轨迹机会有价值，实际收益取决于这些中间条件。
