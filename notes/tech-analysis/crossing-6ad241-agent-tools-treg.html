Treg：三次转型后，怎样在 Coding Agent 生态中找到产品位置

从设计 Agent、自动增长到数据和工具市场，一个小团队如何用真实运营检验“零人公司”，又怎样处理多 Agent 协作的新瓶颈？

完整对话脉络 · 机制与算例 · 独立判断 · 证据边界

先把对话讲清楚

主播 Koji 邀请 Treg 创始人 Jason Zhou 和创始工程师石天鑫，讨论模型能力不断增强时，应用团队还能创造什么价值。两位嘉宾所在团队在九个多月里尝试了设计 Agent、自动增长 Agent，后来把其中的数据与工具层独立出来。官方节目资料将公司写作 Treg；第三方转写多处写成其他拼法，本文采用官方名称。

1. 从周末设计插件到模型能力追赶

Jason 说，最初的 SuperDesign 来自一个周末项目：他观察到设计相关内容有需求，于是团队制作编辑器插件，让用户描述需求，系统给出多个前端或海报设计方案供选择。开源后，项目在几个月里获得六千多个 GitHub Star；他把这看作开源帮助产品被发现的一次经历。

正式创业后，他们一度没有继续以插件为中心。原因之一是插件要求用户先使用特定开发工具，团队希望网页产品能覆盖更广的人群；另一个原因是难以看清开源插件如何收费。与此同时，通用模型的前端设计能力和现成技能不断变强。主持人把这概括为“模型吞噬应用”，Jason 则进一步问：当通用工具也能做得不错，自己提供的增益在哪里？他没有说每个设计工具都必然消失，而是在解释团队为何重新考虑方向。

2. 自动增长 Agent：搭起业务与交付增长是两回事

团队后来做 Crewlet，希望让已有业务的公司使用 AI 自动开展搜索引擎优化、内容、社交媒体和广告投放。促使 Jason 尝试的一次体验是：某个产品只凭邮箱等线索就能帮用户提出创业想法、搭好页面、寻找客户并发送邮件。主持人也体验过，觉得启动过程很顺滑，但后来没有获得收入。Jason 据此区分两种结果：把业务的初始界面和流程搭起来，和持续为真实公司带来增长。

团队发布前就收到一些付费预购，但真正交付后发现增长比预期困难。首先，不同工具的数据分散且不一定准确；其次，营销渠道会变化。以搜索关键词为例，只挑当前流量高、竞争看似较弱的词，可能发现大部分位置早已被占据。更有价值的机会可能需要判断未来一到三个月哪些主题会上升，再持续试验和调整。这个例子说明他们遇到的判断问题；它不构成“SEO 无法自动化”的一般证明。

3. 暂停开发两个月：用自己的产品检验假设

做了一段时间后，Jason 反问团队是否走得太快：他们看到早期 Agent 产品令人兴奋，就假设“零人公司”很快可行，但并没有验证模型能否交付业务结果。于是团队暂停开发新产品，转而用 AI 运营原来的 SuperDesign，把它作为真实实验对象：既有自然流量，也有可以优化的转化流程。

他们搭建并尝试不同循环，发现部分客服和修复工作可以自动化，而增长仍需要较多人判断和测试。Jason 因此判断，在他观察到的未来六到十二个月里，零人公司不是团队应该押注的场景，更现实的问题是人与 Agent 如何协作。这是基于自己业务和当时工具能力形成的期限性判断，不是对所有企业的定论。

4. 插件带来流量，工具层成为新产品

增长实验里有个出乎意料的转折：石天鑫把原有命令行工具和技能发布到一个新出现的 Codex 插件市场，团队几乎没有额外宣传，却看到了用户增长。他补充一个细节：早期市场曾按名称排序，他们把产品名前面加上数字后短暂排到前面；排序规则很快改变，但那几天带来了一些曝光。这个经历说明早期分发渠道可能重要，也说明一次增长里包含具体的平台时机，不能简单归因于插件形式。

团队还观察到这部分用户流失较低，于是决定围绕已有的 Coding Agent 生态做产品，而不是所有层都自己搭。回看 Crewlet，他们发现连接专业数据和工具的一层可能可以单独使用：业务任务需要多个供应商，模型本身不一定拥有最新数据。于是他们把内部中转层发展为 Treg。Jason 说，新产品发布约三周后收入超过旧产品同期水平；具体金额没有披露，所以无法据此评估长期留存或利润。

5. 一个工具市场试图解决什么问题

Jason 将产品类比为面向数据和工具的统一入口：用户在编程 Agent 或自己搭建的系统中，通过一套接口使用不同供应商的能力，按使用量付费。两位嘉宾说，当时较多的需求来自寻找企业客户、搜索排名与社交媒体数据，也有图片和视频生成。他们的理由是：有些信息更新快或需要专门渠道，不能仅靠模型参数中已有的知识回答；浏览器也不一定能取得所有专业数据。

主持人追问，如果最大的供应商直接接入模型公司，中间层为什么还能存在？Jason 的回答是不同供应商覆盖范围和价格不同，聚合方可以帮助用户在具体任务里选择；他把它比作集合多个供应商的零售渠道。石天鑫补充，若工具入口可以跨不同 Agent 使用，用户切换时不必重新建立全部连接。这些是团队对自身定位的解释，能否持续成立要看供应商、平台和用户实际选择。

6. Agent 的反馈能否变成数据飞轮

两位嘉宾还设想让 Agent 在调用工具后反馈：返回内容是否有用、哪些字段起了作用，并把部分反馈用于修复问题或帮助后来的用户选择接口。比如一个任务重视覆盖面，另一个任务重视精确性，平台可能据此展示不同端点的效果和价格。

这条设想包含几个连续步骤：先获得真实任务和调用结果，再收集可解释的反馈，然后判断反馈是否可靠，最后把它用于未来选择。嘉宾说团队已经在尝试一些反馈机制，但节目没有公开完整数据、对照实验或长期结果；“会自然形成飞轮”仍是需要验证的预期。

7. 围绕 Coding Agent 的产品：可编辑状态与多任务管理

主持人举出浏览器和视频编辑插件等例子，说明通用 Agent 周围可能出现专门工具。视频例子尤其具体：如果只得到一段渲染好的成片，每次修改都可能需要重新生成；如果工具保存了片段、音轨和时间线等中间状态，人或 Agent 就可以针对其中一部分调整。Jason 说即便存在可编辑状态，他也可能继续让 Agent 操作，而不是亲自拖动时间线；主持人认同，关键是让修改有合适的对象。

他们也讨论同时运行多个会话后的管理问题：人需要知道哪些任务完成、哪些等待审查，以及上下文怎样在不同工具之间交接。节目提到用通知界面或统一工作台来降低切换成本；具体产品用户量、星标和套餐价格属于嘉宾口述，本文不把它们当作已核实的市场数据。

8. 小循环能做什么，人为什么仍会成为瓶颈

主持人问 Loop Engineering，即围绕任务反复检查和行动的循环，能否支持公司运营。石天鑫把创新和运营分开：他不认为简单循环就能凭空创办公司，但认为监控异常、整理代码等边界清楚的小任务有机会稳定运行。他举出团队遭遇滥用赠送额度的例子：如果一个循环能持续发现异常并提示或处理明确的小问题，可能减轻小团队负担；另一个监控循环还可以发现前一个修改造成的问题。

Jason 说自己已经会并行运行多个会话；石天鑫则发现，人需要同时分派、检查和整合结果，注意力仍有限。他尝试让一个主要 Agent 协调其他会话。两位嘉宾还比较云端隔离环境、本地工作与不同模型的速度和稳定性；这些是各自的使用体验。即使增加并发，是否真正节约总时间仍取决于任务之间的依赖、冲突和最终审查成本。

9. 从原有技能受到冲击，到继续选择创业

石天鑫回忆自己长期做前端开发，随着 AI 编程能力增强，开始重新考虑未来几年想做什么，最终加入创业团队。他的表述很强烈，认为单纯比较写代码的速度，人会越来越难占优；Jason 则觉得设计、产品和工程之间的跨领域能力可能更容易被释放。这是他们从各自经历出发的判断，并不等于某个职业或个人积累已经失去价值。

主持人问多次转型时是否想过放弃。Jason 说最难的是不确定下一步：如果能找到可能改变处境的具体尝试，就继续；如果想不到，就考虑转向。石天鑫也谈到项目遭遇额度盗刷的挫败，以及团队不断寻找新机会的作用。最后，两人解释即使相信模型会继续变强，仍愿意创业：更强的系统可能依然需要及时数据、工具和成本合适的执行方式。节目以他们对未来的乐观收尾，具体商业结果还要看后续。

机制：为什么工具层有时能比端到端自动化更早落地

端到端增长任务的输入可能只是“帮我找到客户”，最终验收却是有效客户和收入；中间涉及目标客户定义、数据获取、内容、渠道、时机、合规和实际成交。任何一环出错，最终结果都可能不达预期。工具层把其中一部分拆出来：接收更明确的数据请求，返回候选结果、价格和字段，由人或上层 Agent 决定如何使用。

本文自拟例子：假设有两个供应商，甲每次返回十个联系人、花费 5 元；乙每次返回二十个、花费 12 元。只看数量，甲平均每个 0.5 元、乙为 0.6 元。但若实际核验后甲只有两人符合目标，乙有八人符合，单个有效联系人的成本分别是 2.5 元和 1.5 元。平台要比较的因此不只是调用成功或返回数量，而是与任务相关的有效结果。这个算例不是 Treg 的实际数据。

即便某接口更便宜，它也只是完整增长流程的一环。数据是否允许使用、联系内容是否合适、客户是否需要产品、后续销售是否完成，都可能决定最终结果。中间层能让选择更方便，却不能单独保证收入增长。

独立判断：这段创业经历能说明什么

一次成功演示，和一个可持续交付的结果之间有距离

团队最初被自动搭建业务的体验吸引，后来在自己的产品上遇到获客困难。这里真正改变判断的，不是对某个模型的抽象印象，而是把目标从“系统完成了哪些动作”改成“真实业务获得了什么结果”。实验可以继续拆细：任务完成率、有效线索、人工接管、成本和实际转化分别记录；否则系统可能生成很多内容，却没有找到真正需要产品的人。

工具聚合的价值取决于替代成本和选择质量

统一接口、按量付费和跨平台迁移可能减少接入摩擦；但若最大的供应商或模型平台提供同样便利，中间层仍需证明自己让用户获得更好的覆盖、价格、可靠性或组合能力。比较时应把接入时间、调用失败、数据质量和总费用一起计算，而不是只看供应商数量。不同数据能否合法用于目标任务也是具体服务需要处理的条件。

Agent 给工具打分，可以是线索，但不自动等于真值

如果 Agent 只能看到接口是否返回了内容，可能偏好字段多、格式漂亮却不准确的结果；如果它自己决定何时评价，还会产生样本选择偏差。更强的验证是对部分结果独立核查，记录任务背景、真正需要的字段、人工判断与后续结果，再看 Agent 的评价是否与这些外部结果一致。只有反馈与最终目标有足够关联，积累更多评分才可能改善后续选择。

增加并发会改变瓶颈，也会增加整合工作

让五个会话各自完成任务，潜在收益来自等待时间重叠；但若它们修改同一代码、依赖同一决定，或都在等待同一个人审查，冲突和审查队列会吞掉收益。应测量从任务提出到结果真正可用的总时间、人工干预、返工和错误，而不是只数同时运行了多少 Agent。小循环的价值也取决于目标是否明确、反馈能否发现错误，以及出现异常时由谁接管。
