访谈脉络：无代码应用怎样从创意走到交付

一个写了二十年代码的人，为什么做无代码产品

朱广翔负责百度秒哒产品，此前在清华做强化学习研究，也长期写代码。Koji 和 Ronghui 邀请他谈用自然语言生成应用的产品、用户和竞争。节目介绍把当时的路线区分为以开发环境服务程序员，和以用户意图为入口生成应用；现实产品可以同时提供自然语言和代码编辑，两者并非只能二选一。

朱回忆，博士阶段曾研究蛋白质三维建模，AlphaGo 战胜李世石后决定换方向做强化学习；他承认换导师和研究方向可能推迟毕业。他后来离开纯编程岗位做产品，认为计算技术不断提高表达层次，人也需要重新选择工作方式。他把「自己做了一个让人不必写代码的产品」说成车轮碾过过去二十年；这是他对个人经历的强烈比喻，不能推出先前的知识没有价值。

他讲了对产品从怀疑到相信的转折：2024 年下半年团队展示的演示依赖工程与人工补充，而看到用户对演示产生自己的应用想法后，他开始相信需求存在。后来他浏览一个网站时被告知那是秒哒生成的；据他介绍，作者是一位五十多岁的医生，为医院制作了官网。这个案例说明他见到了一个实际使用故事，访谈没有公开完整开发过程和系统维护情况。

「用户先赚钱」的倒金字塔

主持人问他为何说不看秒哒自己的 ARR。ARR 通常指按年计算的经常性收入；朱的意思是，先关注用户通过应用创造的业务价值，再设想平台分享其中一部分。他举例，一名用户为门窗店做可视化页面：顾客上传家里照片，选择门窗后查看效果，据称收取 3 万元；另一家原有研发团队的交付公司，据称一个多月交付两个项目，金额分别为 40 万和 30 万。

他还设想未来支持一万个用户，每人创造十几万元收入，平台抽取其中一部分。访谈没有公开样本、合同、收入是否持续或成本；一次项目成交也不能直接称为经常性 ARR。这个乘法表达的是规模化愿景，不能当成已经达成的财务数据。

竞争产品、后端，以及为什么一句话还不是需求

朱按当时体验比较 Lovable、Replit、Bolt.new 和 v0，分别强调轻量开发、后端部署、开发环境和前端设计；他还观察到 IDE、通用 Agent 与工作流平台都在向应用生成扩展。它们的边界会随版本变化，这只是嘉宾录制时的分类，不是对产品现状的排名。

他认为秒哒面向不写代码的用户，要覆盖生成、数据库、发布和运维。前端是用户看到和操作的界面；后端包括保存数据、用户认证和业务逻辑。比如预约页面除了显示按钮，还要保存时间和用户信息，处理重复预约与访问权限。他强调一站式连接后端能减少配置步骤，并称团队可支持大量小型数据库。关于创建数量及同行对比，节目没有给出同口径统计。

Koji 以为秒哒完全不让看代码或操作数据库，朱纠正：当时用户可查看生成代码、通过文字请求修改，也可像表格一样管理数据库的行列，但不能直接编辑代码。是否给用户更大控制权是产品取舍：门槛可能降低，复杂问题的检查、修复与迁移也可能受限。实际能力随版本变化。

他介绍一个产品经理 Agent：用户的一句话先被扩展为需求文档，由用户确认，再交给后续环节生成应用。他认为一句话常常只是创意，例如「做一个预约系统」没有说明谁能取消、时间冲突怎么处理。让用户在实现前补充条件，可能减少误解；文档能否暴露真正的遗漏仍需用真实任务检查。

评估、路由和用户反馈怎样配合

朱说团队将应用生成拆成许多子任务，为各环节设计内部 benchmark，并根据表现选择模型与 Agent 逻辑。他用菜谱、食材和炊具比喻评估标准、模型及路由架构。主持人追问审美如何评价；他承认审美主观，称会结合用户发布、分享、使用行为以及设计师、产品和运营评价。节目没有公开完整测试集、评分规则或路由收益，因此无法评估这套系统的实际效果。

他还描述「反馈飞轮」：点赞、点踩、用户反复修改或发布等行为可以帮助发现问题，进而调整模型和系统策略。他的主张是长期使用能改进产品，并未说明每种行为怎样变成训练标签。发布可能意味着满意，也可能是赶工上线；反复修改可能说明结果差，也可能是用户自己改变需求，不能把任何单个行为直接当作正确答案。

Skills：什么时候加载哪份说明

朱认为 Claude Skills 让按需加载说明和工具的做法更易复用。他回忆秒哒早期长对话修改困难，团队后来让系统先读取说明，再挑选相关工具、代码或上下文，称用户体验有改善。他甚至说可以「无限轮修改」；节目没有公布长周期测试、轮数分布或失败率，不能把它当作无限可靠的证明。

他将插件分为连接外部服务的 API、描述流程的提示词以及执行具体操作的代码。Anthropic 的公开文档同样把 Skills 描述为可分层加载的说明与可选资源，涉及脚本和参考文件；这能节省无关上下文，但并不等于任何长提示都可无修改地在不同平台运行，也不证明两个团队的内部实现完全相同。

「两人三足」与「接力」：对 No Code 的判断

朱认为无代码用户比程序员群体更广，业务专家可能比软件开发者更了解自己的问题。他举一位石油行业工程师制作设计工具的例子，并称先前采购的软件不贴合业务；具体使用和采购金额未独立核验。他说如果重新选择大学专业，可能更早接触计算工具，再学习法律、金融等垂直领域。与此同时，他也希望孩子通过编程学习思维，而非完全取消基础教育。

他把 IDE 中人和 AI 随时协调比作「两人三足」，把用户交出意图、系统执行、最后由人接手比作「接力」，因此看好无代码。他还引用 Sutton 的《苦涩的教训》：长期看，能够利用计算的学习和搜索方法可能胜过大量手工固化经验；由此推断固定 workflow 的空间会变小。后一步是朱对产品路线的延伸判断，原文没有证明所有固定工作流都会被取代。

团队复盘时，他说给模型太大自由会让系统不懂也硬做，但又担心过早设限妨碍未来能力发挥。他承认运营做得晚，团队早期半年没有专职运营。产品自主程度和约束强度如何取舍，是他仍在处理的问题。

「十五度夹角」和模型内化环境的假说

被问如果秒哒失败会因为什么，朱最担心误判模型未来能力：团队做的功能可能很快被基础模型或其官方产品吸收。他用「十五度夹角」比喻：产品要足够依赖模型提升以享受进步，又要有一些短期不能轻易被替代的部分，例如多模型路由、后端、部署或分发。这里的角度并非测量值，也不是已经证明的护城河公式。

他进一步用强化学习中的 model-free 和 model-based 区分引入环境模型：后者可通过学习或使用环境模型来预测状态变化，并在其中规划。他推测编译器和操作系统也是代码，因此未来可能被模型内化；他给出数年尺度，但也承认这是可能发生、也可能不发生的概率事件。这个设想把「预测程序可能产生什么结果」和「真的改变外部系统状态」放在一起讨论，后文会将两者拆开。

云端还是本地？朱认为让新手在云虚拟机里操作可以隔离部分本机风险，也便于并行；但虚拟机内仍有数据、账户、网络和费用约束，不能理解为没有安全问题。他对本地工具的批评来自用户与产品定位的不同，不构成所有工作都应放云端的证明。

大厂内的助力与摩擦

他认为百度为早期投入、算力和产品试验提供支持，使团队能在短期亏损下继续探索；同时，大团队会花时间对齐不同想法。他描述团队将产品、运营、工程、策略坐在一个「十字路口」附近，发生分歧时参考用户反馈。结尾他谈到对 Google 技术、数据和分发能力的看好；这些是个人判断，转写中的个别名称无法确定，节目也没有提供投资研究依据。

机制拆解：一句话怎样变成真正可用的系统

假设用户说「给诊所做预约网站」。系统需要先追问：谁能预约、哪些医生什么时候出诊、同一时段能接待几人、患者如何取消。用户确认后，才有可能生成页面、数据库和预约逻辑。若只生成漂亮表单，但没有保存数据或限制重复预约，用户看到页面并不等于诊所能正常运行。

一次任务可以拆成：理解意图与确认需求 → 生成并连接前后端 → 测试关键规则 → 部署与授权 → 运行后维护。不同环节需要不同反馈：界面可让用户确认；同一时段只能预约一次可通过并发测试验证；是否真的减轻前台工作则要看上线后的实际流程。任何一步成功都不能代替其他步骤。

按需加载也可以放进这个例子。助手先看到工具目录，只在需要数据库迁移时读取相关说明，做界面时读取设计规范。少放无关材料可能减少干扰和成本，但如果把预约限制遗漏，输出仍会错。要比较是否改进，应固定任务和预算，测完整应用的正确性、修改次数与费用，而不只看上下文变短。

独立判断：哪些能力能被模型吸收，哪些仍需外部验证

预测执行结果与真实执行是两件事

一个模型可能根据代码预测「这段程序会输出 3」，也可能在很多例子中学会近似模拟某个编译器。但真实编译器需要对具体语言版本、依赖、输入及错误条件按规则处理；模型的概率性输出必须经过广泛测试，才能知道是否足够可靠。即便它准确预测「文件会被写入」，外部文件也不会因此自动改变，仍需有权限的执行环境完成动作。

同样，模型可以预测某个 API 调用可能返回什么，却不能仅靠预测创造外部支付、查询最新库存或确认实际订单状态。更强的内部模拟或许能减少某些调用，不能自动消除真实环境、授权和反馈。朱给出的三至五年、五至十年是个人预测，节目没有提供可验证的时间推导。

工作流和可扩展学习可以组合

Sutton 原文强调可随计算扩展的学习和搜索；它没有声称任何由人设计的约束都会妨碍产品。对预约系统而言，让模型灵活设计界面与让数据库强制执行「同一时段不重复」可以同时成立。固定规则适合清楚、不能轻易出错的约束；开放搜索适合需求不全或方案空间大的部分。哪个组合更好，应比较完成率、人工负担、成本和错误代价。

行为信号离「用户真正成功」还有距离

假设 100 个用户生成了页面，60 人发布、30 人分享、10 人一个月后仍在使用。发布率回答的是有多少人尝试上线；它不能告诉我们预约有没有重复、患者是否得到确认、系统是否真的节省时间。可以让用户给出关键验收条件，并在授权下检查功能测试和实际使用结果；再按行业和任务分别分析，避免高活跃用户的偏好代表所有人。

模型进步既可能带来替代，也可能扩大产品价值

朱的夹角比喻提供一个实用问题：如果下个月底层模型变强，用户为何还选择这个产品？答案可能是已有数据连接、可靠部署、行业流程、分发或客户关系，也可能因为模型厂商补齐而消失。应把这些能力逐项放在用户任务里测，而不是因为它们现在存在就叫壁垒；同时，模型进步若使更多原来无法完成的需求变得可行，也可能扩大产品市场。
