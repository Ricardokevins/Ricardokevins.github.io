OpenClaw 之后，我只想未来 3–6 个月：对谈 Sheet0 创始人王文锋

本期背景与内容导览

本期是 42 章经创始人曲凯对 Sheet0 创始人王文锋的第二次访谈，距离上次约十个月。两人以 OpenClaw 带起的新一轮 Agent 热潮为起点，讨论它为何能释放 Coding Agent 的能力，以及这种变化对产品、SaaS、团队组织和创业选择的影响。节目发布于 2026 年 3 月；文中的“去年”“今年”均按这一对话语境理解，不把转录中的相对时间擅自换算成别的年份。 王文锋的核心行业判断是：Manus 与 OpenClaw 都通过产品形态释放了模型能力，前者对应深度研究，后者对应代码能力、主动性与自我迭代。他因此提出“最终所有 Agent 都会是 Coding Agent”，并高度怀疑独立垂直 Agent 的必要性。他把传统 SaaS 理解为用交互和流程规模化复制专家能力，认为“Coding Agent＋Skill”也能交付表单、看板、记录等结果，且更容易适应长尾需求。这里的 Skill 在本段不只是工具 API，还包括工作说明、流程和可复用方法。节目中的报告比例、提交次数、用户数和效率倍数，均为嘉宾或主持人转述、估计，未由本期独立核验。 技术讨论随后拆成长程任务、主动性和经验迁移。王文锋认为，把 Memory、Progress 等状态放到文件中，让 Agent 能查看并修改既有状态，再与模型能力和计算机环境结合，是多步骤任务能够纠错的重要工程变化；这不等于文件系统本身保证不再累积错误。对于 Proactive，他区分定时执行任务与在长期上下文中主动发现问题，并进一步设想由 Meta Agent 创建、配置和回收专门 Agent，让需求提出、执行和经验记录形成闭环。团队已经跑通的 Linear—开发测试—GitHub PR 流程，是这一方向的具体实践，但不应与尚属设想的通用 Meta Agent 完全等同。 后半期落到创业选择。Sheet0 正在把内部开发流程产品化，先服务工程师和开发者；王文锋描述的用户画像则包括 Founder、超级产品经理和超级 Builder，共同点是有想法、判断清晰、Ownership 强、能跨领域工作。他认为瓶颈正从“生产代码”转向“定义做什么”，希望把 AI 使用水平约 10 分的人带到 60 分以上。商业化上，他提出按 Token 消耗识别高价值“大 C”，并用“10 万美元×1000 个客户＝1 亿美元 ARR”说明个人或小团队也可能成为大客户；这是商业测算，不是 Sheet0 已有收入，也不代表 Token 消耗与产品收入存在固定换算。 王文锋把去年的失败复盘概括为：试图解决 5–10 年后的“100%可信、可解释、准确”，但模型做不到，用户当时的瓶颈也不在这里。现在他只看未来 3–6 个月，强调“预判为辅、跟随为主”，顺着工程师已被多个 Terminal 占满注意力的现实痛点多做半步。他所谓跟随不是照抄，而是在预判有效期缩短到一两个月时减少沉没押注、快速修正，并放下对差异化的执念。团队经营上，他主张谨慎招聘、提供充分 Token 让人训练，同时由 CEO 对照账单和产出做人工判断；“谁跟不上就淘汰谁”“要么解决问题，要么解决人”等强表述均保留为嘉宾个人管理主张，不写成普遍最佳实践。

  • 最近由OpenClaw带起的Agent热潮，和去年由Manus带起的那一波有什么区别？

曲凯先回顾两次访谈相隔约十个月：上一波 Agent 热由 Manus 带起，这一波则由 OpenClaw 带起，并问两者有什么本质区别。王文锋回答“没觉得有本质上的区别”，共同点不是界面或传播方式，而是都证明了一类新的产品形态能够成立。

他把 Manus 初期的核心场景归为 Deep Research，并把解锁原因归于转录所称“O1 模型”的推理能力。这里谈的是 o1 一代的推理能力。“Swilling”的准确词形仍待回听，不扩写成另一种模型能力。对于 OpenClaw，他承认有人会把火爆归因于能在 Telegram、Discord 等 IM 中方便调用，但他自己的解释是：它把最新模型的 Coding 能力释放到了此前没有想到的程度。IM 是入口，Coding 能力及其产品化才是他强调的因果主张。

王文锋进一步把这次产品信号连接到 Proactive Agent、自我迭代和自我进化：这些概念此前已被讨论很久，却缺乏可见的跑通形态，OpenClaw 让他看到一种实例。因此，“新形态成立”是他的产品判断，不等于主动性、自进化已经在所有任务上被充分验证，更不等于两个产品的技术架构相同。

Agent本期泛指能围绕目标规划步骤、调用代码或外部工具并交付结果的 AI 系统。嘉宾谈的并非只有聊天，而是能持续执行任务的系统。
Coding Agent以代码、Terminal、文件和开发工具为主要行动接口的 Agent。嘉宾强调它与基座模型的 Coding 能力不同：前者还包括释放能力的工程和产品层。
Skill本期语境中既可包含工具调用方式，也可包含工作说明、SOP 和可复用方法论。嘉宾认为它能把垂直经验带给通用 Coding Agent，但没有证明所有隐性知识都能被完整 Skill 化。
Step 与长程任务Step 是 Agent 执行中的一次中间动作，如读文件、访问 API 或调用 Tool；长程任务强调更多步骤和更长状态链。步数多表示链长，不自动等于结果可靠。

曲凯重提“AI Coding 是大模型的灵巧手”。王文锋认为这已经得到现实产品验证，并给出更强的预测：“最终所有的 Agent 都会是 Coding Agent。”这里的 Coding Agent 不只是会生成代码的模型，而是能围绕代码、Terminal、文件和工具执行任务的系统；他强调基座模型的 Coding 能力与 Coding Agent 是两回事，后者负责把能力释放成可用结果。

他用 OpenClaw 的内部结构作例：他把执行任务的编程智能体和外围的记忆、消息渠道分开。同期 OpenClaw v2026.3.8 的架构文档给出了准确组件名 Pi。OpenClaw 把 Pi 的会话嵌入消息网关，再接入工具、会话持久化和不同聊天渠道。访谈里相邻的另一个英文词听写不清。

在嘉宾的叙述里，去年的思路是针对不同应用场景搭环境、做 RL 和定制策略，垂直接口与经验难以复制；现在则可用 Coding Agent 配合 Skill，把这些经验带到具体场景。他把 Manus 称为模型 API 时代的极致“壳”，把 OpenClaw 称为当前 Coding Agent 的一种优秀“壳”，并认为谁能做好这一层是今年机会。这里的“所有”“没有场景做不到”是他的强判断，并未由节目逐项验证；同时“壳”承担的是能力释放、记忆、连接和使用门槛，不应简化成没有技术含量的包装。

话题推进：这一强判断引出路径选择：过去一年的通用 Agent、Agent 平台和垂直 Agent，究竟哪些仍然成立？

00:05:29–00:11:20垂直Agent路线存疑，SaaS模式面临根本性挑战

  • 回顾过去一年，Agent赛道出现了通用Agent、Agent平台、垂直Agent等不同路径，现在来看这些选择有无对错之分？
  • 未来在企业服务（2B）领域，是否会出现像抖音在内容领域那样一家独大的平台？这家公司有没有可能就是OpenAI或Anthropic？

曲凯回顾通用 Agent、平台和垂直 Agent 三条路线。王文锋说，虽然“很不愿意承认”，垂直 Agent 现在需要被高度怀疑，因为 Coding Agent＋Skill 已能实现许多过去由垂直产品承担的效果。曲凯把讨论推进到 SaaS，嘉宾则转述一份其所称的 Anthropic 报告：Claude Code 的使用场景中 49.7% 为 Software Engineering，其余超过一半包括办公自动化、数据分析、Marketing 和 Copywriting。这里有一个会改变结论的分母。Anthropic 2026 年 2 月的研究图 6 确实说软件工程接近一半，但统计对象是公共 API 上的单次工具调用。一个任务可以调用许多次工具，同一客户也可以通过别的产品访问 API。它显示智能体已被用于其他领域，无法据此计算 Claude Code 用户的非编程任务占比或成功率。

曲凯接着问，企业服务是否会出现类似抖音的统一平台。王文锋没有直接预测赢家，而是先解释过去为何会有大量垂直 SaaS：专家经验和决策能力过去要靠长期培训分发，软件把方法固化成交互和 UI，使用户按流程操作便能获得部分专家能力。由此，软件价值不只是“代码写得出来”，而在于规模化复制工作方法。

Agent 改变的则是获取这种能力的方式：用户描述目的，Agent 提方案、执行和迭代，不必先学习每套 SaaS 的界面。曲凯补充，传统 Best Practice 是面向许多公司的通用专家，AI 则可能提供随企业情况变化的定制专家。王文锋进一步认为，过去把长尾需求收敛到 Best Practice 是因为逐一满足不划算；如果 AI 执行不同流程的成本接近，Best Practice 的重要性会下降。他最终预测会有统一系统解决绝大多数需求，但不确信是 OpenAI、Anthropic 还是其他主体。

曲凯的质疑很具体：Skill 还很简单，为什么一家公司发布一套 Skill，相关行业 SaaS 的股价就会下跌，它真能替代复杂工作流吗？王文锋回答“现在倾向于是”，并把质疑归结为对模型能力的怀疑。他给出的类比是，把一份工作说明交给真人，真人学会其中工具后可以完成；模型也在沿这条路径发展。他甚至说模型已到了“人一样”的地步、替代 SaaS 已被证明。这里保留其判断强度，但它不是本期提供的跨行业能力测评。

他给出的更具体理由是输出等价：SaaS 将 SOP 固定成操作和交互，产出表单、Dashboard 或记录；Agent 也能交付这些产物。如果 Agent 的使用门槛继续降低，他认为多数人就缺少继续使用旧界面的理由。这个论证比较的是任务结果和交互成本，尚未覆盖权限、责任、持续可靠性等采用条件。

随后他用开发案例说明能力上限。转述包括：OpenClaw 作者在产品火之前某天最多 1600 次 commit；Cursor 内部用 Agent 一周做出 300 万行代码的浏览器；转录另说某官方团队“断断续续”实现了一个“CVE 的编辑器”，具体编辑器未能辨清。就浏览器而言，Cursor 当年 1 月的工程记录写的是接近一周、约 1,000 个文件、超过 100 万行，没有给出 300 万这个数。1600 commit 被嘉宾类比为三四人技术小组一年的工作量，这是他的直观估算，commit 数与代码行数都不能自动换算成有效工程产出。

王文锋由此把瓶颈从技术天花板移到认知和使用：他设想每月花两三万美元 Token 的顶级用户是 90 分，多数人只有 10 分，并判断效率差距是非线性的，善用者可能达到千倍效率。90／10 与千倍都是说明差距的口语估计，不是量化评测。他认为接下来既要让人知道能力已到哪里，也要解决怎样把 Agent 配好、用好。

- 输入：已经被用户反复遇到、能观察到的瓶颈，例如工程师同时管理十几个 Terminal。

- 过程：团队总结共性问题，在已经显现的大方向上快速形成产品，交付后依据反馈修正产品方向与重点；比当前需求多做半步。

- 输出：面向未来 3–6 个月的可售产品和下一轮回馈。

节目案例重述（非独立实测）

【按嘉宾去年与今年产品选择的对照重述】去年的 100% 可信目标人人认可，但当时模型做不到、用户也未因此停用，属于价值正确却未击中瓶颈；现在工程师已被多窗口管理拖住，自动化任务接收和 PR 则直接减少当前协调成本。这是嘉宾用来说明‘顺需求多做半步’的对照。

独立判断：这些对话改变了什么理解

‘所有 Agent 都是 Coding Agent’最有解释力的部分，是代码和文件提供了通用行动接口；它最薄弱的部分，是把行动接口统一推成领域知识不再重要。

推理：同样是修改文件、调用 API 和运行脚本，确实可以服务研发、办公、分析等不同任务，这解释了 Coding Agent 为何可能穿透传统应用边界。但任务能否完成还取决于 Agent 是否知道目标、约束、异常和验收标准。Skill 可以承载显式 SOP，却未必低成本承载隐性判断、组织责任与长期关系。按 Anthropic 图 6 的分母，软件工程约占公共 API 工具调用的一半。其余调用发生在哪种任务、一个任务要调多少次、最后是否交付，是三个不同问题。

竞争解释与边界：更稳妥的检验不是问产品名字是否叫垂直 Agent，而是比较同一领域任务中‘通用 Agent＋Skill’与专门产品在成功率、配置成本、异常处理和审计上的差异。若通用方案无需领域资产也能持续胜出，嘉宾的强判断才得到更有力支持。

文件系统让长程任务更可修复，但也把‘执行错误’部分转化为‘状态与验收错误’，不能据此宣布误差累积问题已经解决。

推理：内存中的暂时过程难以回改，文件则让 Agent 和人都能检查中间状态，这确实增加修复机会。但 Agent 必须知道真实结果是什么，才能发现 Progress 记错；如果错误同时进入代码、测试和记录，文件越持久，错误状态反而越容易被后续步骤信任。因此，持久化不是正确性的来源，只是反馈和修复的载体。

竞争解释与边界：评估长程系统应分别记录任务完成率、错误发现率、修复成功率与错误传播，而不只看 Step 数。 hundreds 或 thousands of steps 只有在这些指标不显著恶化时才代表能力扩展；否则只是更长的错误链。

Sheet0 的内部流程证明了限定工程环境中自动化的可行性，但‘个人 10 倍’和‘两周做产品’还不能直接外推为公司产出或商业结果。

推理：Linear、GitHub、Lark、测试和 PR 构成了清晰任务源与反馈链，适合自动化，这比泛称 AI 已能主动工作更有证据价值。不过，个人编码速度、团队交付速度和用户需要的产品是三件事。需求澄清、架构责任、测试缺口、维护与用户发现仍可能成为瓶颈。嘉宾自己也把问题转向产品定义，说明代码生产加速并不自动给出值得做的产品。

竞争解释与边界：若要验证团队效率，应固定任务类型与质量要求，比较自动化前后的交付周期、返工、线上缺陷和维护成本，并同时记录 Token 支出。若只统计 PR 或代码量，容易把生产数量误当有效产出。

‘只看 3–6 个月’是一种降低预测暴露的组织选择，它的价值在快速获得真实反馈，而不在跟随本身带来高胜率。

推理：嘉宾复盘的关键不是长期目标必然错误，而是旧目标同时缺乏当前模型可行性和用户迫切性。转向现实瓶颈能让每次交付更快提供证据，减少为错误预判辩护的沉没成本。但如果所有团队都根据同一热点行动，跟随会提高竞争密度；频繁改向还可能破坏数据、客户关系和工作流资产的积累。

竞争解释与边界：判断这一策略是否有效，应观察 Sheet0 能否在短周期交付中形成难以随下一次转向带走的资产，例如高频用户需求、可靠评测、分发和深度工作流。本文不建议机械套用‘80% 跟随＋20% 探索’这类无来源配额，而建议用资产积累和真实采用检验每次修正。

按 Token 识别高意向用户是一个有用信号，但 Token 更像成本与使用强度指标，不能单独代表客户价值。

推理：高消耗者往往已把 AI 纳入工作，因而更可能需要管理、配置和协作工具；这支持 Sheet0 先服务重度用户。但 Token 也可能来自低效重试或错误任务，且不同模型价格差异很大。嘉宾本人后来仍要由 CEO 对照账单和产出，实际上已经承认消耗与结果需要分开。‘1000×10 万美元’只能说明 ARR 算术，不能证明客户愿意持续付费。

竞争解释与边界：商业上更需要同时观察 Token、有效交付、留存和客户预算来源。若产品收费与 Token 成本解耦，模型降价可能扩大用户价值；若只是转嫁消耗，价格变化和效率提升都可能削弱收入。

尚未解决的问题与可检验的下一步

待解问题：通用 Coding Agent＋Skill 在哪些领域足以替代垂直产品，哪些领域仍需要专门资产？

下一步信息或小实验：选择一个具有明确交付物、异常流程和权限要求的非研发任务，在相同输入上比较通用方案与现有垂直产品。记录初始配置时间、任务成功率、异常处理、人工返工、审计证据和总成本，并披露 Skill 编写投入。

怎样的结果会改变判断：若通用方案在多个领域以更低总成本达到同等或更好质量，‘垂直 Agent 需要高度怀疑’更有依据；若大量成本转向知识整理、权限和返工，则应把统一行动接口与领域专门化重新分开。

待解问题：Sheet0 的自动化开发流在实际团队中带来的净效率和质量变化是多少？

下一步信息或小实验：连续记录一批相似任务，区分需求澄清、开发、测试、返工、合并与上线后维护；对照接入前后的周期、人工时间、Token 成本、缺陷和回滚。另抽样检查 AI PR 是否真正满足需求，而非只有测试和截图。

怎样的结果会改变判断：若净周期显著缩短且缺陷、返工没有恶化，嘉宾的效率判断得到支持；若时间转移到需求返工和维护，‘两周做产品’就需要限定为生成首个版本。

待解问题：文件化与 Meta Agent 能否改善长程任务，而不是只延长执行链？

下一步信息或小实验：在同一批多步任务上比较无持久状态、文件化状态和带任务调度的版本，统一模型与工具预算，记录完成率、错误发现、修复成功、错误传播和成本。再加入一个故意写错的中间状态，观察系统能否发现。

怎样的结果会改变判断：若步数增加但完成率和修复率不改善，就不能宣称长程问题已解决；若文件化能稳定发现错误、调度又能减少人工介入，才支持嘉宾提出的共同作用机制。

待解问题：3–6 个月跟随策略能否在快速交付之外积累可持续优势？

下一步信息或小实验：跟踪 Sheet0 数次产品修正，记录每次保留下来的用户、评测、数据、集成和分发资产，以及活跃使用和付费留存；同时比较同方向跟随者的进入数量和差异化。

怎样的结果会改变判断：若短周期迭代不断形成复用资产与留存，说明跟随并非简单追热点；若每次转向都重置用户和工作流、又没有独特分发，‘优化胜率’可能只是提高忙碌程度。
