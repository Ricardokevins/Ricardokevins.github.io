闫俊杰等：模型、工程验证与领域专家

从模型规模和多 Agent 协作，到“代码能写出来，却没人敢上线”：讨论 AI 如何成为可持续的生产力。

对话脉络 · 训练与验证 · 独立判断 · 证据边界

先把对话讲清楚

Koji 在 MiniMax 开发者活动现场主持圆桌，嘉宾包括 MiniMax 创始人闫俊杰（IO）、Multica 创始人张佳圆、DeerFlow 核心负责人何涛，以及金融行业 AI 负责人虞扬。讨论从模型能力和使用情况开始，转向多模型工作流、金融应用、长期维护软件以及领域专家怎样参与模型研发。

1. 一代模型好不好，为什么看使用量

闫俊杰回忆团队做 M1 时已经感受到模型能解决编程问题，但产品效果还不理想。到 M2，团队主动把重点放在编程和编辑，不以所有通用对话评测为主要目标；后来随着 Agent 工具出现，模型找到了相应使用场景。他说团队曾以每天消耗一万亿 Token 为目标，后来达到约十万亿，明显超过当初预期；对更新模型也有更高目标。

官方简介与机器转写对这个例子涉及的具体 M2 子版本并不一致，本文保留总量与超出预期的口述，不替其中一个版本做判定。Token 是模型处理文本等内容时使用的计量单位；用量增长可以反映使用规模，但还受价格、重复调用、上下文长度、客户数量及任务类型影响，不能单凭它证明模型质量或商业利润。

2. 多模型配合与开源项目

张佳圆说团队处理代码 issue、客户支持等任务，未必每一步都需要最贵的模型。他们尝试让一种模型负责生成，再让另一种模型审查或指导，以平衡质量和调用成本。他也说实际系统会遇到模型啰嗦、思考耗时长、结果并非全部正确等问题，因此需要根据任务安排不同模型。节目没有展示可复现的成本和准确率对照。

何涛介绍 DeerFlow 起初想把研究报告、图表及其他多媒体工作做成可复用的开放工具，后来也成为需要维护的大型开源社区。他坦承项目受欢迎有偶然传播因素，并提到大量外部贡献、代码质量和社区协作带来的维护挑战。节目中的项目星标与贡献者数量是活动时的口述。

3. 金融场景：从信息列表到下一步

虞扬说，不少用户只会提出“帮我选股票”这类宽泛目标，却难以说明具体需求。产品如果只是罗列信息，用户仍不知道它对自己意味着什么；他希望 AI 帮助解释术语、筛选信息并组织下一步判断。他也说团队有内部回测，但公开输出受相关要求约束；访谈没有提供数据、策略、交易成本或样本外结果，不能据此评价投资表现。

主持人追问模型建议能否直接用于交易，他指出市场会变化：除了预测事情可能怎样发生，还要考虑事情发生后怎样调整行动。信息解释、历史回测和真实交易的收益是不同层次，需要分别验证。

4. 基础模型与 Agent 是竞争还是互补

闫俊杰认为很难提前一年准确预测最终形态。他把基础模型与 Harness 都看作实现任务能力的手段：模型提供理解和生成能力，Harness 是围绕模型组织上下文、工具、循环和执行的系统。更好的模型可以让 Agent 完成原来做不到的事，而好用的 Agent 产品也可能让模型能力被更多人使用；两者可以共同进步。

5. 走向更大模型的困难

主持人问 10T 规模模型的挑战。闫俊杰说，扩大训练规模不只是多买算力：模型结构、训练效率、数据质量和系统都要变化。他认为经验规律只能有限外推，规模增加若干倍后需要重新实验；他设想先积累较小一代的经验，再尝试更大的模型。

他用“参数量乘以 20”估算训练数据规模，并以 10T 参数、200T 数据说明挑战；这是节目中的粗略假设，不是所有模型和训练阶段都必须遵守的公式。这里的 T 表示万亿，参数数量、训练过程中处理的 Token 数以及去重后的独立数据量也不是一回事。他同时对不同地区的模型大小差距和自家进步速度作出判断，节目没有提供完整可比数据，不能作为独立排名。

6. 会生成代码，为什么还交付不了

张佳圆说，当写代码的门槛降低，项目维护者更需要决定做什么、不做什么，并让外部贡献者理解共同的产品方向。何涛补充，一次解决 issue 和长期维护代码库是不同任务：软件工程要考虑后续修改、可读性与持续交付；单次基准通过后，下一位维护者是否还能安全扩展，未必有答案。

闫俊杰举过一次多仓库开发的观察：一个人可以借助 AI 同时提出覆盖多个仓库的大改动，功能看起来完成了，却没人敢上线，因为验证和评审没有跟上。他认为模型和工具不应只追求更快地产出代码，也应投入接近生产环节的能力做测试、评审与交付。他提到端到端测试、任务基准和项目原则等方法，但没有给出它们足以解决所有问题的证据。

何涛反对把责任推给“代码是 Agent 写的”：当成果由开发者的账号提交，仍要有人对质量负责。他也提醒模型道歉并改写不一定意味着原来一定错，人需要保留判断。

7. 数据为什么需要领域专家

闫俊杰说，做编程模型时团队逐渐发现，专业软件工程师比单靠模型研究人员更容易判断什么是好的工程任务、测试和强化学习环境。扩展到金融、法律等领域时，他认为需要模型研究、工程实现与领域知识一起工作；专家不只是给已有答案贴标签，还可帮助定义真实问题、评价标准和可执行的反馈环境。

他提到 MiniMax 的专家合作计划，并观察其他模型公司会引入多种学科背景。节目说明了为什么需要这种合作，没有公开完整的数据构建方式、专家分工或合作成效。

8. 医疗交流、人的思考与理解 AI

最后张佳圆讲了家人的经历：通用聊天工具给出的建议没有解决困扰，他尝试整理体检、检查和就医记录，让个人 Agent 帮家人准备与医生沟通的问题。这个例子展示整理背景和准备提问的用途，不能证明模型建议安全有效，也不能替代医生判断；敏感健康数据如何授权和保存同样重要。

何涛说自己愿意和 AI 共同探索，但希望把核心思考留给自己。闫俊杰则关注 AI 能否帮助人理解 AI：模型中存在许多尚未解释的现象，自动化工具也许能帮助研究。关于大脑机制与神经网络相似的说法是他的类比与判断，访谈没有证明大脑训练等同于反向传播，或者某个记忆系统已经复现海马体。

机制：从生成补丁到安全交付

本文自拟例子：一个支付系统要新增退款规则，Agent 同时改了服务、数据库迁移和前端。单次测试只验证“退款按钮返回成功”，并不能发现重复请求是否会重复退款、旧版本客户端能否使用、迁移失败后账目是否一致。

一条更完整的流程可以先定义业务不变量：同一订单退款累计金额不能超过已支付金额；再让系统生成补丁，运行正常、重复、并发和失败恢复等测试，检查相关仓库的接口变化，最后由有权限的人依据风险审查并决定上线。一次通过测试只说明被测试条件下的表现；真实系统还需要监控和回滚能力。

让第二个模型审查第一个模型可能发现遗漏，但两个模型若依赖相同错误假设，仍可能共同通过。外部测试、真实约束和可复现反馈提供的是不同类型的证据；模型之间互相同意并不自动构成独立验证。

独立判断：领域知识怎样变成训练信号

专家不仅提供答案，也定义什么值得检查

以编程为例，研究员可以设计训练算法，工程师可以提供会真实发生的变更任务、故障条件、测试和维护约束。模型生成方案后，环境执行测试并返回结果，训练系统才有可能利用这些反馈。扩展到金融时，还需要明确数据时点、预测目标、可交易约束和成本；“专家在场”本身不保证反馈可靠。

这也指出一个更开放的问题：即使模型能把既定 issue 修好，它是否能发现尚未写成 issue 的架构风险？可比较两种设置：一组只给明确任务，另一组给运行记录和项目目标，让系统主动提出风险，再由独立维护者和后续实际问题评价。提出更多建议不等于发现更重要的问题，应看可验证性、遗漏与误报。

用量、参数和任务结果各回答不同问题

每日 Token 消耗描述处理规模；参数规模描述模型的一部分资源配置；端到端任务质量描述在特定输入、工具和预算下完成了什么。三者可能相关，却不能相互替代。比较方案时，需要同时说明模型与工具配置、任务难度、时间成本和质量，避免把更多调用当作能力增长。

更快的生产会把瓶颈推向验收

当生成改动的速度超过团队理解和测试的速度，未验证的改动会积累。与其只增加生成并行度，更值得衡量的是单位时间内有多少改动被正确验证、可以安全交付，并在后续修改中继续工作。某个项目应投入多少验证资源取决于风险和现有测试，而不是机械地把访谈中的比例当成规定。
