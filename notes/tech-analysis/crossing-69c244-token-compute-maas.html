于文渊：Token 增长背后的算力、服务与工程判断

从 Agent 请求增长讲到 GPU 调度、云与自建、系统软件生成，以及工程师如何保持判断力。

对话脉络 · 推理服务算例 · 独立判断 · 资料与边界

先把访谈讲清楚

Token 需求为何让云服务承压

Ronghui 采访阿里云百炼研发负责人于文渊，讨论模型服务的资源与工程问题。MaaS 是 Model as a Service：用户通过服务接口调用模型，由服务方处理模型部署、资源调度和运行维护。嘉宾说，随着编程助手和 Agent 被用于真实工作，平台的 Token 使用量快速增长，某些模型发布后峰值请求量创下其内部纪录；这些是他在特定时间看到的平台情况。

他提醒，一枚 Token 不是统一的算力单位。小模型与大模型、短输入与长输入、生成过程中是否需要额外计算，都可能有不同成本和延迟。主持人提到「一天消耗一亿 Token」的重度用户群，嘉宾认为单看数量容易误导，更应结合使用的模型、服务质量和完成的任务。节目对用户数和增长的口述没有公开统计定义。

对云服务来说，负载增长不是只买更多 GPU：同时运行的模型、训练与推理需求、请求的峰谷、首字输出等待时间和生成速度都要协调。于文渊希望尽量利用 GPU，同时保持稳定和安全。他把长期愿景描述为让大量分散资源通过接口弹性服务用户；这并不意味着现实中任何 GPU 都能永远满载。

从聊天到业务，服务商提供什么

他举饮料经销商补货的例子：客户在群里说需要什么和多少，系统结合既有信息理解需求并对接订单流程。自然语言让入口更容易使用，但准确识别商品、确认数量、连接库存和处理异常仍由完整业务流程决定。节目没有披露这一案例的错误率或人工接管情况。

他认为模型服务的竞争包括模型质量、吞吐、延迟、稳定性、成本和可用容量。以同一开源模型为例，不同部署方采用的推理框架、精度和调度不同，用户体验可能不同；他也强调阿里云与模型及芯片团队的协作。作为服务提供方，他对自家服务效果的评价应结合独立基准和用户实际负载理解。

企业自建还是使用云服务

主持人问什么情况下企业应该自行购买 GPU 和部署模型。于文渊提出非常绝对的个人看法：没有必要自建。他的理由是，自建不仅要买设备，还要随模型变化持续优化推理、安排负载、保障可靠性；服务商聚合多个客户后可能更容易利用资源。对安全，他介绍了「机密推理」方向，希望用户持有密钥并限制服务商接触模型和请求；对灵活性，他认为云服务更容易应对模型和硬件变化。

这一看法有其服务商视角。访谈没有给出具体产品配置、信任边界或客户对照，不能把「服务商完全看不到任何数据」推广到所有云服务。是否自建还取决于数据和合规要求、负载是否稳定、硬件利用率、内部团队、网络和退出成本；后文用算例说明。

学计算机与使用 AI 写代码

于文渊仍建议学生学习计算机，也应学会使用 AI。他担心初学者把每一步都交给模型后，缺少识别错误的经验：原型写得出来，并不自动满足生产环境对资源、并发、故障和维护的要求。他反对把 AI 生成代码占比作为单一目标，认为工程师应理解系统的行为和副作用。

他提到规范驱动开发：由人把目标、接口和约束说清楚，再让模型生成与检查实现。他举一篇 FAST 文件系统论文为例，认为清晰规范能帮助较小模型处理复杂任务。论文与访谈的具体对应及实验边界见下文；不是任何任务都有现成规范，也不能保证规范本身没有遗漏。

嘉宾进一步预测，接口和测试相对明确的底层工作可能比开放式产品问题更容易被自动化，而离用户更近的「什么产品真正有用」难以只靠一组测试定义。他同时认为 MaaS 系统工程面对快速变化的硬件、模型和需求，仍有开放问题。这是对任务性质的区分和职业趋势判断，不意味着操作系统工程没有开放研究，也不意味着前端工作都无法自动化。

算力供给与未来云服务

他把算力比作石油：不仅要问能否生产，还要看供给增长能否赶上需求。他看好国内工程能力，但担忧短期供需缺口；对没有亲自使用过的芯片，他没有给出具体测评。关于未来，他认为 Agent 和生成任务会继续消耗算力，也看好沙箱、搜索和可观测性等把底层复杂度封装起来的服务，对单纯转售裸算力更谨慎。

他相信模型服务会像公共基础设施一样被广泛使用，但不同模型仍会在质量、速度和功能上存在差异，不会像同一种电压的插座那样完全等价。这是他对行业发展的预测。

为什么吞吐量、等待时间和成本不能只看一个数字

处理一个模型请求通常先处理输入上下文，再逐步生成输出。前一阶段常称 prefill，后一阶段称 decode。假设两位用户各提交相同数量的输出请求，但第一位给了很长的代码库背景，第二位只问一句话；即使最终生成 Token 数相同，输入处理、缓存占用和首字等待也可能不同。不同模型和服务实现还有额外差异。

本文自拟例子：一台服务同时收到四个请求。若逐个处理，每个请求的计算时间都是 2 秒，最后一个请求要等到前面三个完成后才开始；如果硬件与模型允许把它们组成一批，四个请求可能在更短的总时间内完成，但为了凑批次等待太久又会让第一个用户更慢。实际耗时取决于请求长度、设备和调度，例子只说明吞吐与延迟需要一起设计。

缓存可以避免重复处理部分相同上下文，但会占用显存；提高并发可能提高设备利用率，也可能让每个用户等待更久或超出内存。因而服务指标至少要结合请求成功率、首字等待、后续生成速度、单位任务成本和不同负载下的质量，而不是只看 GPU 利用率或 Token 数。

独立判断：怎样把强观点变成可比较的选择

自建与云：先算总成本和约束

本文自拟例子：企业如果自建，一年的设备折旧、机房电力、维护人员与运维合计 120 万元；使用云服务的调用、网络及集成合计 90 万元，云在这个负载下便宜 30 万元。但如果负载大幅增加、设备高利用且模型长期稳定，结果可能反过来。还应计入质量要求、峰值冗余、闲置时间和团队机会成本；不能只用显卡采购价对比 API 单价。

安全问题也不能用「云绝对可信」或「自建天然安全」一笔带过。需要说明数据在哪里解密、密钥由谁控制、可信执行环境及其证明覆盖哪些部分、日志和运维人员能接触什么，以及组织接受哪些责任。不同云产品和部署方式可能有不同答案。

SysSpec 的规范为什么有帮助

与嘉宾描述最接近的公开论文是 FAST 2026 的 SysSpec。它把文件系统设计拆成功能、模块关系和并发约束等结构化规范，再通过生成和验证流程构造实现。论文报告生成的 SpecFS 在数百项回归测试中与人工实现基线达到相近的正确性水平，并评估了多个模型与功能；规范并非严格完整的形式化证明。

论文确实测试了 Qwen3-32B 等模型，但文中明确报告在特定 45 个模块实验中达到 100% 的是更强的 Gemini-2.5-Pro 和 DeepSeek-V3.1；不能将该结果笼统归给 32B 模型。更重要的是，人工设计规范、分解模块、验证代理、测试与人工检查都参与了结果。它说明明确约束可以改善生成，并不证明几句提示词就能安全生成任意生产文件系统。本文只核对了论文摘要和相关实验段落，未复现。

学习不必在「全手写」和「全交给 AI」之间二选一

初学者需要形成可独立调用的判断：例如先预测一个并发程序可能怎样失败，再让模型生成实现，用测试和实际输出核对自己的预测；也可以让 AI 解释陌生代码，但必须能说出关键输入、状态变化与错误条件。随着熟练度提高，自动化范围可以扩大。是否理解，比机械统计手写行数更能反映学习效果。

开放问题也需要反馈

「什么是好的产品」难以由一个固定测试穷尽，但仍可通过观察用户任务、保留反例和比较替代方案逐步检验；系统问题也不只剩执行，选择架构目标和发现未知瓶颈同样开放。更有用的划分是：哪些部分已有可靠验收，哪些判断需要人与系统共同补充信息，而不是给整个职业贴上可替代或不可替代的标签。
