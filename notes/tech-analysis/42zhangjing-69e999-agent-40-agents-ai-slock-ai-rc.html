Slock.ai创始人RC访谈：构建人与AI Agent协作的动力学与未来组织形态

本期背景与内容导览

RC从Kimi CLI的开发经验出发，讨论面向Agent的CLI、local agent harness与多界面产品路线，再解释为何离开Kimi创建Slock：他希望自由组合不同模型，并解决个人多session难管理、团队成员的Agent经验难共享两类问题。节目主体不是单纯介绍群聊，而是围绕共享channel/thread、任务认领、连续session、external memory、共享文档及AI/AX展开一套人机共同工作空间的设想。 审读后需要把证据分成四层。RC描述的当前实践包括7人和40个Agent、在channel发任务并claim、在thread中长程纠偏、以memory.md为启动入口，以及因review带宽不足引入真人负责。Alice纠正Bob、模型组合效果与竞争导致‘办公室政治’属于RC的产品观察或用户访谈转述，尚无对照数据。共享文档、Marketplace/fork、部分自动工具发现、公司模板和定价方式处于计划、探索或roadmap。模型漏洞导致秩序变化、3—6个月追赶、AGI后产品形态等则是趋势推演。 因此，‘Agent动力学’目前更适合作为一组待验证问题：什么信息应进入哪个Agent的context，何时共享经验能减少重复纠偏，何时排他认领能避免重复执行，何时人的判断与责任成为瓶颈。1、1.1、1.5等生产力数字是类比，不是实验；70分与90分是主观示意；‘代码没有意义’是RC强调过程价值的强观点，不能取消可执行产物与验收的重要性。

00:00:20–00:03:04什么是CLI？为什么它在Agent时代重新流行？

  • 什么是CLI？
  • 为什么现在大家都在做CLI？
  • CLI听起来很基础，有什么值得做的？
  • 当下的CLI是给Agent做的最早的产品吗？

主持人曲凯介绍Slock.ai创始人、Kimi CLI作者RC，先请他为非技术听众解释CLI。RC将CLI解释为Command Line Interface，即通过文本命令使用计算机的程序；GUI则是图形界面。他的判断是，大模型以文本为主要交互媒介，命令行的文本输入输出因此重新变得重要。这里“模型天然不适合读GUI”是嘉宾的概括，不等于Agent无法使用视觉或图形界面。

RC进一步区分了给人用的传统CLI和给Agent调用的新型CLI。后者的输入应简洁、明确，帮助文档与manual应给出例子，降低错误调用；输出应明确报告操作是否成功、返回了什么，并尽量确定、静态且信息密度高。他举的例子是让Agent列出飞书消息：每条消息都应清楚带出发送者与发送时间，供Agent继续处理。

曲凯提出“CLI是否是最早给Agent做的产品”，RC没有接受这个归纳。他回溯computer use Agent：通过截图或accessibility API获取电脑状态，有时把结构化的、甚至XML形式的信息喂给模型；他认为那条路线效率较低，但今天仍有人在做。因而本段提供的是接口路线的比较与嘉宾经验判断，并非CLI已经取代GUI或computer use的证据。

00:03:04–00:08:30Kimi CLI的开发理念：从第一性原理出发，不把CLI视为终局

  • 为什么你们是25年8月才开始做Kimi CLI？
  • 你们在做（Kimi CLI）的过程中跟Claude Code借鉴的部分多吗？

曲凯问及“25年8月”开始做Kimi CLI的时间点。RC先澄清两个不同层次：Kimi CLI是给人使用的、长在命令行上的coding/general Agent；它调用的其他CLI才是面向Agent的工具。RC说，Claude Code和Gemini CLI证明了local agent的价值，而他想亲自弄清Agent如何从基础loop发展到能读文件、操作浏览器、完成复杂coding任务；Kimi当时缺少此类产品，于是他从side project开始探索。原转录没有给出可独立核对的正式立项日期。

RC并不喜欢把terminal当作终局。他的设计是让CLI成为面向程序员的第一种界面，底下沉淀可复用的local agent harness，再封装SDK，在其上增加Web UI和VS Code扩展。他自述团队在中后期已引入这两种界面，离开前已铺开后继路径。对SaaS，他又区分说，Notion、Linear等面向Agent呈现时应重视CLI形态。这些是产品路线与他对不同用户的判断，不是“所有Agent最终都必须使用terminal”。

关于借鉴Claude Code，转录把回答者标成曲凯；从提问和第一人称经历看，这段只能按RC自述理解，仍建议回听确认。RC说他从几十行agent loop和空system prompt起步，先给Agent一个被转录为“batch tool”的命令执行工具，再逐步增加任务难度，观察它为何做不好，由此增加built-in tools并修改prompt。他称当时没有大量参考Claude Code及开源coding agent，而是想从第一行重新推导，以获得新insight。“命令工具理论上能做任何事”不等于只给工具就能稳定做好任务；他的实际方法恰恰包含失败驱动的工具与上下文迭代。

00:08:30–00:15:32模型能力军备竞赛：乐观共存与潜在风险

曲凯以“Claude新模型因太强不敢发布”的传闻提问未来coding能力。随后转录中的“Methods”“OPAS/OPAC”等名称存在疑点，本稿不替原音确定具体模型。相关第一人称回答从语境看是RC的观点，但说话人标签有误。RC设想，更强模型若加速发现银行系统、Linux kernel、编译器和Chromium等基础软件的漏洞，攻击方因利益驱动可能快于修复方；他希望政府与大公司投入更多token，让防御方更早发现并修复漏洞。他还转述安全从业者“已经完蛋”的担忧，并推测安全公司的价值可能降低。这些都是风险推演和转述，不是新模型能力或漏洞已经被节目证实的结论。

另一条攻防线是网站访问。RC以转录中某款把网页操作沉淀为 CLI 的工具为例，认为具体项目名在机器转录中未能确认；他认为模拟真实浏览器与人的操作会促使网站加强防御，工具方再模拟验证码处理、鼠标延迟等行为。他由此判断，Agent能力提高会同时增强攻防双方。曲凯随后转述“Anthropic泄露、模型自主上传”的未经确认真假的新闻，RC只回应“理论上可以发生，只要给它access”，并未确认该事件。

RC自称人与Agent的“共存派”、相对乐观。他预期模型厂商会加强拒绝黑客与伤害行为的训练，也提到通过参数激活区域寻找模型行为关联的研究设想；这不能证明拒绝训练已经解决权限滥用或安全问题。他补充，自己的项目会反复prompt Agent找漏洞并修复，因此可能不需要庞大的安全团队，但也保留“可能需要专门安全人员”的余地。

最后，曲凯问复制两行文字给Agent安装软件是否属于CLI。RC把它解释为软件开始把Agent当作用户：人只需理解软件能带来什么能力，Agent去读skill并安装CLI；他把“skill + CLI”概括为“prompt + 命令执行工具”。他以转录中的DB9临时数据库工具为例，提出未来人只说“你自己把数据存好”，Agent应自行发现、安装并使用工具。这是他希望减少安装与选择负担的产品愿景，同时隐含工具可信度、权限和验收问题，本期没有展开验证。

RC设想，一个比现有模型强得多的新模型发布后，可能会让全球依赖的开源软件（如Linux内核、Chromium）的漏洞完全暴露。攻击者利用AI发现漏洞的速度会远超防御者的修复速度，可能导致“世界崩溃”。

RC提到，一些把网页操作转化为 CLI 命令的工具可以用于数据抓取，具体项目名在转录中未确认。这引发了工具开发者与网站反爬虫机制之间的“军备竞赛”。工具方致力于更逼真地模拟人类行为，而网站方则不断升级防御。

RC畅想，未来用户甚至不需要手动执行安装命令。当用户告诉Agent“你自己数据存好”，Agent应该能自主上网搜索，找到一个叫“DB9”的临时数据库工具，阅读其说明，并自行安装使用，整个过程无需人类干预。

00:15:32–00:19:38离开Kimi创办Slock：为人与多Agent协作构建新平台

  • 你在Kimi工作的感受是怎么样？
  • 那你最后为什么决定离开Kimi呢？
  • 你讲讲看你现在在做的事情吧。

曲凯从人才密度和年轻人话题问RC在Kimi的感受。RC说自己最初被Kimi的“摇滚精神”吸引，入职后感受到的突出优点是ownership：有能力与意愿的人可以获得较大的scope。他以自己此前没做过AI、但side project显示价值后获得负责机会为例，称公司未必百分之百信任一个人，却敢bet他把事情做成。这是RC个人经历与组织感受，不能推广为所有员工或团队的统一机制。

关于离开，RC说一月初形成创业idea，当时认为需要frontier模型，在Kimi内部做可能受限；独立创业可以自由采用多种模型、支持不同Agent，保持diversity。这是他对自己决策的解释，不是对Kimi模型能力的完整评价。

Slock要解决的问题有两层。第一，个人在本地开多个Claude Code/Codex session，会忘记各自用途、需要逐个追踪进度；不同任务出现交集时，又只能人工复制一个session的结论给另一个。RC说这是开发Kimi CLI后期的真实痛点。第二，团队成员的偏好、想法与调教经验沉淀在各自Agent中，其他人难以看见、复用。

他的产品设想是把一群人和一群Agent放进共同协作环境：可以调自己的或别人的Agent，人与人先讨论、头脑风暴，再拉Agent参与，讨论后直接说“你们直接做吧”，减少上下文搬运、重新prompt和知识重组。本段描述的是正在建设的产品及其目标；并未给出协作效率、知识复用率或团队产出的对照数据。

00:19:38–00:24:25Coding与Building正交化，编程学习路径的Top-down转型

  • （Slock）现在就是比较专注在coding这个领域里面，是吧？

  • （对于学不学编程）你站哪一条？

RC不同意把Slock限定为coding产品。他认为过去想build软件通常必须自己code，所以builder与coder高度重合；现在没有编程基础的人也可借coding Agent构建东西，因此build与code在他的表述中趋于“正交”。这里的正交是指构建意愿不再必然要求亲自编码，并非软件质量、工程责任或技术知识都变得无关。

他按任务区分编程基础的价值：做软件时，懂编程的人更能理解Agent在做什么，并减少漏洞等问题；做go-to-market时，他观察到一些非技术用户在Slock上调研、发推、寻找KOL合作、看评论，反而用得更顺。他把这解释为这些人更像对人一样直接提目标，例如让Agent去看小红书或推特，Agent会自行搜索工具并执行。这里是RC对部分用户的观察，不能推出“非技术用户普遍优于程序员”，也没有披露任务成功率与质量验收。

关于是否还学编程，转录把RC的一段长答标为曲凯。按上下文可理解为RC提出的top-down学习路径：先用prompt做出网站；不满意时，再拆解Web架构、前后端、部署与数据库；规模从约千人到数百万、数千万的举例中遇到瓶颈，再进一步学习数据库种类与部署。千人、百万等是说明学习触发点的假设量级，不是性能测量。传统bottom-up则先学组成原理、汇编、C语言，再进入应用开发。

曲凯追问为什么AI不能自己学、是否会有标准skills。RC回答可以像雇架构师一样把问题交出去，但人至少要知道“我要招一个架构师”。因此他保留的不是人人必须精通底层，而是人能识别问题、知道需要何种能力并作判断。AI能否自行补齐这层问题识别，本期没有验证。

Slock上有用户使用Agent进行市场调研、在Twitter上发帖、联系KOL等自动化任务。RC发现，没有编程背景的用户反而用得更“溜”，因为他们直接用自然语言与Agent沟通，把它们当成能自主解决问题的“人”。

RC · 00:22:25

RC描述了新的“Top-down”学习编程路径：一个人先用AI生成网站，当需要优化时才去了解Web架构；当用户量暴增导致性能瓶颈时，才被“倒逼”去学习数据库和部署等更底层的知识。

00:24:25–00:26:04人月神话在Agent团队中的重现：成本与效率的权衡

  • （一个群组里有47个“人”）这样聊天，它应该会非常费Token吧？
  • 你自己现在每天大概平均消耗多少Token？

听到RC公司有7个人和40个Agent后，曲凯先问群组沟通是否很费token。RC没有统计自己的token消耗，而是借《人月神话》说明：增加成员带来communication cost，产出不会按人数线性增长。他用“一个人生产力1，两个人可能1.2”作类比，再把一个、两个、十个Agent的产出分别设想为1、1.1、1.5。所有这些数字都是解释协调损耗的假设，不是Slock实验测得的吞吐量。

RC的目标不是证明多Agent一定划算，而是先让系统支持单个Agent做不到的工作，再改善token efficiency。他提到task系统、thread与channel隔离等机制，希望十个Agent的总产出能向2或3提高；2或3仍是目标性举例，不是已有实验结果。要判断是否值得，需要同时比较任务完成质量、时间、token费用和人的监督成本，而本期没有这些基线。

当曲凯追问每天平均token量时，RC再次明确说没有统计，只描述自己每天的工作就是在Slock里与Agent讲话。因此本段不能以“40个Agent”推导成本，也不能把“费Token并不一定是坏事”理解为成本无需约束。

RC · 00:25:03

RC类比《人月神话》解释多Agent协作的成本：增加人力或Agent数量会带来沟通成本，导致生产力无法线性增长。例如，10个Agent的合力可能只有1.5，而不是10。 该数字是类比假设，并非实测。

RC · 00:25:44

Slock通过引入任务系统、线程、频道隔离等机制，来优化多Agent协作的效率，目标是让10个Agent的合力能从1.5提升到2或3，同时提高Token使用效率。 这里仍是目标性举例，未披露对照实验。

00:26:04–00:28:07人与Agent的团队配比：一个在演化中探索的动态数字

  • Slock.ai团队为什么是7个人和40个Agent？这个配比是如何决定的？
  • 为什么不能用Agent替换更多的人，或者增减Agent的数量？

他的具体例子是：人在channel看到稳定的界面、频道列表和新消息，能凭连续记忆理解变化；Agent接收的却是线性context中的messages/events。一个Agent可能先收到A频道消息、执行一串动作，再收到B频道消息；旧thread的新回复离原话题很远时，系统需要让它知道当前回复关联哪段历史。RC认为只给message ID不够，至少还应给此前消息的summary，帮助唤醒相关上下文。他认为这对long context索引构成挑战，并批评只用“大海捞针”衡量这类能力不够。具体模型版本在转录中不清，不能据原稿猜写。

第二类问题是多Agent同步。消息发布后，模型往往默认自己应该处理，导致十个Agent都抢任务。Slock当前的做法是prompt要求先claim，再由工具以类似exclusive锁的方式保证一个任务被认领后别人不能重复认领。RC同时指出模型 teamwork能力不足：即使系统有锁，模型仍须理解何时应行动、何时让同伴处理；他把这视为模型厂商也需改进的方向。排他锁只解决认领状态，不自动解决任务拆分、执行质量、异常释放或重复副作用，本期未讨论这些实现细节。

曲凯问能否@指定Agent。RC观察到，即便prompt告诉Agent“你是Alice”，模型也未必稳定响应针对Alice的请求，有时聊着聊着会忘了身份。现有缓解包括调整system prompt、检查是否真的忘记，并适时重申身份；@时只把消息发给指定Agent是“可能做、现在没有做”，不能写成已上线路由。RC刻意克制这类补丁，理由是预期模型变强后可能不再需要；这是他的路线取舍，不是补丁必然无用的证明。

他还对比“每个channel/topic给Agent开独立session”和“一个Agent一个连续session、看到其所有channel消息”的理念。Slock选择后者，容忍重复执行与冗余消息，以保留跨频道经验。RC举例：Alice经反复纠偏做对后，下一次同类任务可减少调整；若Bob在同一channel犯类似错误，Alice可能根据可见对话纠正Bob。这里“Alice会调整他”是RC观察到的行为描述，不能直接写成稳定质量控制，也不能把两个Agent误写成共享同一context；准确说法是各自有session，同时可看到共同channel中的对话。

待解问题：多Agent相对同预算单Agent究竟带来什么净收益？

下一步信息或小实验：固定任务、模型、工具与总token预算，比较单Agent多次迭代、单主Agent带子Agent、多个平级Agent加channel三种设置。除最终任务通过率外，记录wall-clock、输入输出token、人干预次数、人审查分钟及重复副作用。至少覆盖可并行调研和强耦合软件修改两类任务。

怎样的结果会改变判断：若多Agent只在可并行任务有净收益，Slock应优先支持任务分解与选择性协作；若在强耦合任务也稳定减少错误且人工审查下降，连续共享channel与Agent动力学才显示出更普遍价值。1.1、1.5等示意数字不能替代这个实验。

待解问题：一个Agent一个连续session的收益来自哪里，何时被噪声抵消？

下一步信息或小实验：比较每频道独立session、一个连续session但只给当前消息、连续session加相关thread摘要三组。测试旧话题回复、身份@、同类错误纠正与无关任务干扰，并测量正确关联率和token。

怎样的结果会改变判断：若相关摘要能以显著较低token达到相同纠错率，就说明关键不是无边界共享，而是事件选择与上下文组织；若连续session稳定提升跨任务迁移，则RC的设计获得更直接支持。

待解问题：external memory能否可靠保存、检索并迁移能力？

下一步信息或小实验：让Agent完成带独特约束的任务，写入memory后清空context并重启；测试原任务、相似任务和看似相似但约束相反的任务。再将memory复制到同模型不同Agent和不同模型，检查正确复用、旧经验误导及入口漏检。

待解问题：claim机制能否保证任务层面的恰好一次，而不只是记录唯一认领者？

怎样的结果会改变判断：若负面行为主要由措辞诱导且不影响结果，应把它视为可控生成风格；若跨任务稳定出现信息隐瞒并降低质量，才更接近需要组织机制处理的行为问题。
