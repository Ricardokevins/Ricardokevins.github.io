一、「模型以外都是 Harness」：机甲比喻、5 万星教程与范式之争

Koji 开门见山：如果只用一句话向完全没听过这个词的读者解释，什么是 Harness？来新璐答得极干脆：「模型以外都是 Harness。」模型像一颗极其聪明的大脑，但没有身体和手脚就只能空想、无法行动。面对业内流行说法「Agent 的上限由 Harness 决定」，他只赞成一半：智力上限的拔高终究靠模型本身，但如今主流模型换算成人类智商大约已在 120 到 170 之间，早已足够聪明；Harness 的角色如同给高智商大脑套上一副机甲（或是学武术、健身、跳舞）——它不直接提高智商，却把行动半径放大了数个数量级。

回溯 5 万星教程 《Learn Claude Code》 的起点，那其实是 9 个月前他自己整理的一份「造 Code Agent 心法」。当时他有一个朴素直觉：Claude Code 太强了，只要给它套个网页壳就能做出极强的 Agent 产品。但那时开源圈几乎一边倒地追捧 LangChain、LangGraph 那套基于 Prompt 节点、路由和条件状态图的 Prompt Flow-Driven 做法——开发者普遍不信任模型自主流转，总想每一步自己画死流程，觉得既省钱又可控。来新璐把这看作一场根本性的派系与范式之争：老路线（Prompt Flow）在未来会越来越不适用，而 Claude Code 代表的 Agent-Native（模型即 Agent、Agent 即模型）路线会迅速成为主流。

恰逢录音前几天 Anthropic 推出了托管服务 Claude Managed Agents，Koji 拿云计算作类比追问：云服务器早期工程师都要钻研底层 Infra，后来 99% 的项目直接调 API 即可，两三年后大家还用学 Harness 吗？来新璐借前端框架 Next.js 坦然承认：两三年后 Harness 确实会收敛成开箱即用的基础设施，届时多数开发者不必深究底层原理；但此刻正处在技术周期剧烈变动的红利窗口，如果不懂 Harness 的内核，做出来的产品必然「缺乏灵魂」，也找不到后续迭代抓手。

Koji 顺势问到产品经理需不需要懂这一层。来新璐直接亮出锋利判断：「今天的产品经理和过去的产品经理，根本已经不是同一种人。」过去可以靠画好 UI/UX 胜任，但今天做产品本质上是在把技术周期变化的红利翻译进具体场景——你必须一手懂场景痛点，一手懂底层技术究竟在变什么。

二、把 Harness 拆成三层：用「两周多 Agent 写 C 编译器」一以贯之

为了把抽象概念落地，来新璐将 Agent Harness 清晰切分为三层——简言之即「会跑（执行层）→ 跑久（状态层）→ 跑稳（治理层）」，并用那个轰动行业的经典案例——「多 Agent 协作两周从零构建一个 C 编译器」——将三层完整串联：

  1. 第一层：执行能力层（Action）。给模型装上手脚，包括 CLI、代码注册工具以及 MCP 扩展工具。来新璐认为配齐三类核心工具即可覆盖 95% 以上的 Agent 任务：第一是文件系统工具（增删读写搜索，无论 Coding 还是 Deep Research 都是刚需）；第二是 Browser（浏览器），让模型能直接操作既有的人类软件与网页世界；第三是 Python / Node 等语言解释器。这一层最易踩的坑是权限错配：例如专职 Explore（代码库探索）的 Agent 绝不能赋予写入、修改或删除等有副作用的命令，配备浏览器时也必须严格收紧可访问网域白名单。
  2. 第二层：上下文与状态层（Context & State）。模型开始干活前，必须清楚所处环境、当前路径、已装依赖、目录结构、Git 历史，以及 System Prompt、Skills 与 Memory。更关键的是长程任务的窗口限制：如今主流模型窗口约 256K，远不足以一次性写完整个 C 编译器，因此必须设计上下文卸载（Offload）与接力棒交接机制——当窗口逼近上限，当前实例要把代码写到哪了、环境状态如何、下一步做什么写成清晰文档，让下一轮新窗口无缝接棒。
  3. 第三层：治理与编排层（Governance & Orchestration）。当系统里不是 1 个而是 100 个 Agent 同时运转，就等同于管理一家百人公司：哪些模块可以并行写、哪些必须串行交接、任务怎样委托与汇合？更重要的是角色权限隔离——在 C 编译器案例中，负责跑测试的 Agent 绝不能同时拥有修改代码的权限，否则一旦测试不通过，它就会顺手去改代码甚至改测试用例来「Hack Pass」，把整个验证体系搞穿。

三、为什么自建「1KB Unix 虚拟计算机」？K 系列工具链与云沙箱之辩

面对 Koji「这三层现在有哪些封装得比较好、哪些还要手搓」的追问，来新璐直言从 2022 年底 ChatGPT 到近半年真正能跑长程任务的 Agent 模型，范式迭代太快，开源界尚无让他满意的封装——这正是 Komputer Blue 亲自下场构建 K 系列开源工具链的缘由：

组件定位与核心机制解决的工程问题
Komputer用 TypeScript 在内存中以纯数据结构实现最小化 Unix 文件系统与闭集 Bash；支持 WASM 时自动切换 Rust 实现，否则回退纯 JS极致轻量至 1KB 级（类似一个 Map 结构），覆盖浏览器纯前端、插件、Electron、App 与仅几兆包体限制的微信小程序，让 Agent 以为自己活在熟悉的 Unix 机器里
KruntimeAgent Runtime 层，提供面向人类开发 Agent 以及 Agent 派生 Agent 的接口与语法糖类似前端时代的 Vue / React，让开发者在任意 JavaScript 场景直接 import 使用
Kwatch观测层，追踪过去半个月 Agent 的成功路径与卡点分布反向诊断瓶颈到底出在 CLI 设计、Skill 缺失还是基座模型能力
Krl基于观测导出轨迹，支持模型强化学习训练；或对只调标准 API 的用户自动提炼更新 Memory / Skills把上线轨迹变成持续进化的燃料；上下文自迭代路径被他戏称为「穷人版的强化学习」

Koji 犀利追问：云厂商早就盯上这一层（AWS 有 AgentCore，阿里云有 AgentBay），且 Manus 用的云沙箱 E2B 与 Daytona 也已成熟，创业公司拿什么打？

来新璐给出的差异化极为明确：第一是运行位置贴近用户——不是全塞到云端，而是让所有能跑 JavaScript 的轻量端侧环境无差别跑起 Agent；第二是虚拟化颗粒度的彻底革新。过去一年多数沙箱只是往旧方案里硬塞浏览器、做成臃肿的 All-in-one 虚机，并无本质跃迁。Komputer 在纯数据结构层就还原了 Unix 文件系统、虚拟 Bash、前后台进程、虚拟时钟、局域网磁盘共享以及基于 Mail 和 HTTP 命令行请求的局域网通信。

他毫不回避其中的 Trade-off（权衡取舍）：这个 1KB 级虚拟环境确实无法本地运行真正的 GCC 编译器或真实浏览器。但从他多年大厂做系统性能优化的经验出发，这反而是更合理的架构——分析整条 Pipeline 时，本就该把低频调用但极耗资源的重工具（如编译器、浏览器）从单个 Agent 独享环境里抽离出去，改为后端集约化公共 Infra 服务，而不是给每个 Agent 都配一台笨重昂贵的完整 Linux 虚拟机。

四、Memory 三流派与 Claude Code 源码泄露的四大工程惊喜

谈到第二层的核心模块 Memory（记忆），来新璐将当前尚处早期探索期的方案划为三派：第一派是完全结构化/规则式（知识图谱 + 向量检索 + 节点规则推理），他明确表示不喜欢；第二派是半结构化/半规则式（底层是 Unix 文件系统 + 大量 Markdown，人定好清晰的目录或空间关系——例如近期颇受关注的类迷宫空间记忆项目、开源项目 MemU，以及 Claude Code 与 OpenClaw 自身——再交由便宜小模型在后台按流程负责检索、整理与更新），他高度推崇；第三派是完全模型内化（按官方简介整理，距生产落地大约还需 3 年，且存在记忆难以无损迁移、被单边模型厂商锁定的风险）。

Koji 提起 Y Combinator CEO Garry Tan 开源个人记忆一事，指出业界如今越来越分不清 Memory 与 Skill 的边界：追根溯源，是 Claude Code 去年底推出的 Insights 特性（回看近一个月对话、诊断成败与错误并生成报告反哺 Skill），以及近期 Hermes Agent 的记忆自进化把两者揉到了一起。来新璐与主持人顺势引用 Generalist AI 发布 Gen-1 模型时的博客名言——「不要用标签定义自己，要用目的定义自己」——达成共识：它们本质上都属于上下文层的经验沉淀，标签不重要，能不能帮 Agent 持续变强才重要。

当 Koji 请他复盘 Claude Code 源代码泄露带来的最大收获时，来新璐拆出了四个干货极密的内部机制：

  • 与 Skill 同源的双层记忆体系（实时 Fork + 后台「悄悄做梦」）：
    ① 实时层（Stop Hook + Fork Agent）：每当一轮任务结束，系统触发 Stop Hook，立刻派生一个 Fork Agent——它完整继承原 System Prompt 与历史上下文、直接复用 KV Cache，低成本判断本轮有哪些新事实值得写入 Markdown；而且记忆 Markdown 严格沿用和 Skill 一模一样的结构哲学——文件前三行是 YAML 元数据（写清 description），平时只扫文件名与描述、按需才加载全文。
    ② 后台整合层（Auto-Dream「悄悄做梦」）：该特性仍由远程 Feature Flag 控制未全面面向普通用户开放。每隔大约一天且累计满足超过 5 个 Session 的条件时，系统会在后台启动一个 Agent 对近期会话做一遍完整重放，榨干遗漏信息、纠正过时或错误的旧事实、合并冗余条目——宛如人类睡眠做梦时的记忆巩固。
  • 多级上下文压缩与「接力棒」工程兜底：面对 256K 上下文装满但任务尚未完成的困境，Claude Code 设计了多级策略——初级先踢掉上下文里的垃圾与过长工具输出，往往立刻腾出几十 K 空间；进阶则设定容量阈值（例如 0.8，留足 20% 缓冲），整理出一份交代总体目标、当前进度与下一步计划的交接文档，把「接力棒」递给下一个新初始化的 Agent 按需续跑。
  • 彻底的「Zero Control」哲学：整个源码贯彻「模型才是 Agent」——更少的控制（Less / Zero Control）、更多的上下文（More Context）、更充分的行动能力（More Action），最多只在工具层做权限禁用，绝不靠程序员手写庞大状态图替模型做每一步决策。
  • 从底层运行原理解读工程抽象：如同计算机史上从 CPU → 汇编 → C/C++ → Python / Node.js 一层层长出适配硬件的抽象，今天的新底层硬件是自回归 Transformer 模型。只写传统前后端 Rule-based 代码的人往往看不懂 Manus 或 Claude Code 为什么这样设计上下文管理，但只要顺着 Transformer 推理机制倒推，所有最佳实践都会变得顺理成章。

五、好与坏 Harness 的两条铁律，以及「CLI is all you need」

主播 Ronghui 紧接着抛出一个核心问题：到底什么算好的 Harness，什么算坏的 Harness？来新璐亮出了两条极其清晰的第一性原理判准：

  1. 必须与模型推理运行自洽：最典型的反面教材，就是随意裁剪中间轮次、删掉早期消息或频繁改动 System Prompt——这会导致 Prompt Caching / KV Cache 频繁失效，迫使模型反复重算。他甚至抛出金句：「最好的上下文管理就是不要做管理。」
  2. 必须与模型未来能力的进步正交：随着基座模型越来越强，模型 + 你的 Harness 必须水涨船高，而不是像旧式 Prompt Graph 那样模型越聪明越被硬编码节点捆住手脚，最后被迫像 LangChain 一样不断推倒重写。在来新璐眼中，Linux / Unix 就是对模型最强的正交 Harness——「哪怕将来模型进化成 ASI，它也只会更会使用 Linux。」

Ronghui 追问能否用 Token 消耗效率（Token Efficiency）评判 Harness 优劣。来新璐认为目前还不必过早卷这一项：Anthropic 是从 2025 年初率先从问答模型转向 Agent 模型训练的，包括 OpenAI 在内的其他厂商到 2025 年下半年才开始追赶、落后约半年，因此整个行业仍处在 Agent 模型的「婴儿期」。当下工程策略很简单——紧贴 SOTA（Anthropic）与次 SOTA（Kimi、MiniMax、GLM 最新一代）贴身构建即可。

给做好一个 Agent 的核心要素排序时，他毫不犹豫地排成：第一，模型（任务做不好，换更强模型最立竿见影）；第二，上下文（对没有千卡集群改权重的普通开发者而言，文件夹、OS 环境、Skills、Memory 与交接策略才是最大发力点）；第三，工具。

在工具协议的路线之争上，来新璐旗帜鲜明地站队 「CLI is all you need / Bash is all you need」——这正是他 9 个月前写在 learn-claude-code 仓库里的标语，如今已成行业共识。他分享了自己的亲身转折：2025 年 3 月他曾深度使用 GitHub MCP，省去了反复打开网页忍受 3 秒加载的麻烦；但后来试了 GitHub CLI，发现能力覆盖和任务成功率远胜 MCP，当即把 GitHub MCP 卸载了。近来爆火的飞书 CLI同样在组合性与完成率上全面领先旧版插件。他给出一个极为扎实的预训练语料归因：Unix 从 1971 年沿用至今，大模型预训练语料里包含数十亿条 Linux 命令样本，极其鲁棒；而 MCP 诞生才两年，在预训练语料中占比可能不到 0.1%，且 Shell 天然自带管道组合与二次编程空间，行业正在「返璞归真」。

六、三个看好的创业方向与压轴暴论：「零人公司」与口袋里的黑色卡片

访谈尾声，Koji 请这位 23 岁的年轻创始人展望创业版图与终局图景。除了自己正在深耕的 Agent Harness 开发者工具链（他清醒预判该赛道竞争必将极其惨烈、且由于必须同时满足「自洽」与「正交」最终只会收敛出极少数派系——如 Unix/Shell 轻量派与 TypeScript 严格结构化派——但他依旧笃定推进，因为未来地球上运行的 Agent 数量可能是人类的几百倍，为它们搭建自建、派生与协作的基础设施就是当下对「加速世界升级」最大的杠杆），他还点名了另外两个极其看好的方向：

  • 方向二：Agent-Native 混合全设备组网。不是简单给 Agent 配 IM 或邮箱，而是把云端服务器、手边 Mac 笔记本、Mac mini、路由器、NAS 与闲置手机等无公网 IP 硬件全部打通。旧式 FRP 内网穿透难以规模化；他很欣赏 Tailscale 的极简局域网体验，但认为它不够 Agent-Native（CLI 操控能力欠缺）。Agent 间需要的是高通量上下文交换——类比当下讨论的 B2A Agent Payment（几分钱几分钱的高并发微支付，完全不同于人类低频大额转账）。
  • 方向三：集约化 PEFT 训练 + LoRA 热插拔推理基础设施。展望十年后，如果所有人还在调同一个通用模型 ID 未免太过无趣。他极力推崇 OpenAI 前 CTO 创立的 Thinking Machines Lab（Tinker 项目）路线：用高速互联大集群大幅压低 PEFT（参数高效微调）成本，推理时只需在 API 请求 Header 里挂上专属 LoRA 权重瞬间热插拔，哪怕仅多付约 5% 推理成本，就能让每个企业或个人拥有持续贴合自家 ERP、CRM 业务的个性化参数模型——这正好与 Komputer Blue 收集的轨迹数据形成完美上下游互补。

最后，Koji 索要几条面向未来的「暴论」。来新璐先勾勒出清晰可见的四阶演进（预计当前 Agent 模型阶段持续约 3 年）：单体 Agent → Agent 蜂群集群化作业 → Agent 自主管理并编排更多 Agent（直接写进训练目标）→ Agent 成为真正的「发明者」（自主提出科研假设并迭代实验）。

顺着这条曲线，他抛出了让后来多期播客反复引用的核心判断：「我从来不觉得一人公司（OPC）是本质，真正 Make Sense 的是零人公司（0PC）。」在他看来，客户从来只在意一家公司的输入和输出，没人天天跑进你办公室盯过程，公司内部本就是黑盒；未来许多由经验丰富的人类团队搭起、甚至由 AI 直接生成并自运转的公司，本质上会变成一种「理财产品」。Koji 立刻联想到真格基金与《十字路口》Token Grant 资助的 yoyo Agent（创造者造完即丢进公海、永不改代码不给钱，定下「超越 Claude Code」的目标，靠 GitHub 打赏「化缘」买 Token 自我迭代），感叹未来资本投资的标的可能真的不再是人类公司，而是独立的 Agent。

来新璐用一幅极具赛博朋克感的画面结束了整场对话：「未来你可能是个大老板，走在路上碰到朋友，从口袋里掏出一张黑色卡片介绍说：这张卡片里跑了 5 个公司，每年给我创造几十亿收入——这就是我的公司，它就在这张卡片里。」

三层联动演练：把「执行—状态—治理」放进一个具体编程任务

本文自拟可复查任务：假设需要修复一个开源工具库中的日期解析 Bug，同时确保既有的十余种历史日期格式全部向后兼容。

  • 执行层（Action）：Agent 拿到工单后，先用只读搜索命令定位解析函数与相关单元测试，通过解释器跑通最小复现脚本；确认根因后在授权目录内修改源码、补写边界用例并重跑回归测试。没有文件读写与命令执行能力，模型只能纸上谈兵。
  • 状态层（Context & State）：假设排查涉及多处时区与历法库依赖，上下文窗口很快逼近 80% 阈值。此时交接文档绝不能只写一句「正在修日期 bug」，而必须沉淀结构化接力信息——需求兼容列表、已复现的最小失败输入及命令、已排查但排除的假设、当前改动的具体文件与行号、尚未验证的边界条件。下一轮新窗口读取接力文档后，仍应先复查当前文件状态与最新测试结果，防止外部环境变化或上轮误判被顺着放大。
  • 治理层（Governance）：若采用多 Agent 分工，治理层须把「修复者」与「验收者」的权限硬隔离——修复者有源码写权限但无法改动隐藏验收测试集；验收者仅拥有只读源码权限与完整测试执行权。如果多个修复实例并行处理不同格式分支，治理层还需引入文件锁或分支合并规则，防止彼此覆盖改动。

独立分析：哪些判断站得住，哪些仍需实证对照

1. Anthropic C 编译器案例的启示：赢在反馈与拆分，不只赢在多 Agent 数量

对照 Anthropic 公开的项目记录，该实验调动 16 个实例、历经近 2,000 次会话，消耗 API 费用约 2 万美元，通过文件锁与共享仓库减少冲突。一个极容易被忽略的关键转折是：当多个实例集体卡死在 Linux 内核构建的同一处报错时，人类研究者介入并引入 GCC 作为参考基准（Oracle），只让自制编译器处理部分源文件，才把整块不可解的大故障拆成了可并行定位的子问题；研究者还持续补写测试、改进报错反馈并清理回归缺陷。这说明，多 Agent 协作能够推进超长程工程，前提是高质量的外部验证器、清晰的故障隔离与人类对反馈回路的工程打磨，而非简单堆砌实例数量。

2. 「Zero Control」的真实边界：放开探索路径，但锁死副作用与验收

来新璐批判 LangGraph 式硬编码状态图会随模型变强而成为枷锁，这一观察已被近两年 Agent 工程演进充分验证。但把「减少流程硬控」简称为「Zero Control」容易在落地时引发误解。更准确的工程原则是把「推理路径自由度」与「系统边界约束」分开处理：允许模型自主决定查什么文件、试几种修复思路、怎么组合 CLI 命令；同时在工具执行层严格锁死权限、不可逆外部副作用（删库、外发数据、资金操作）以及隐藏验收标准。哪里放手、哪里加护栏，取决于操作可逆性、验证客观度与失误代价。

3. CLI 与 MCP 并非零和替代，而是不同抽象层的能力互补

来新璐从预训练语料分布（「1971 年起的数十亿 Unix 命令样本」vs「诞生两年的 MCP 占比不足 0.1%」）与 Shell 管道可组合性解释 CLI 成功率更高，这是一个极具启发性的技术假说，也贴合不少一线开发者的体感。但从架构上看，CLI 是面向本地/终端进程的人机与机机交互界面，MCP 是规范宿主应用与远端工具、资源及鉴权上下文交换的标准协议——二者不在同一层，一个 MCP Server 完全可以在底层封装 CLI，而跨组织鉴权、细粒度 OAuth 权限边界、强类型参数校验与云端多租户部署恰恰是裸 CLI 的短板。要严格比较两条路径，必须在相同任务集、等价底层能力与权限配置下，控制接口文档质量与预算，分别量化完成率、调用轮次、总耗时、Token 成本与误操作率，才能分清差距究竟来自协议本身、实现质量还是模型熟悉度。

4. 前缀缓存、上下文压缩与长期记忆，三者不能混为一谈

「最好的上下文管理就是不要做管理」精准点破了 KV Cache 失效带来的隐性成本灾难，但若将其绝对化为「永远不清理历史」，同样会撞上长窗口注意力稀释与信息噪声问题。工程上需分清三件事：前缀缓存负责复用不变前缀降算力与延迟；窗口压缩 / 接力负责在逼近容量上限或工具输出刷屏时做有损腾挪；长期记忆（Fork Agent + Auto-Dream）负责跨会话沉淀稳定事实与偏好。尤其在科研与复杂排错场景里，压缩或「做梦」一旦错误删掉反例或把偶然现象写进长期记忆，反而会导致后续会话系统性盲从错误前提——因此长期记忆必须附带来源溯源、时效标记与纠错回滚机制。

5. 「零人公司」的乐观跃迁，仍绕不开法律主体与责任归属

与同期 MiniMax 嘉宾坚持「人的品味与目标定义不可替代」形成有趣对照，来新璐把公司抽象成「只看输入输出的黑盒理财产品」，极富未来感。但即使技术上 Agent 蜂群实现了自我运维、自动获客与代码自迭代，现实商业世界里的公司并不仅是输入输出函数，还承载着法律契约主体、监管合规、资金托管、侵权追责与声誉担保。在「口袋里的黑色卡片」成为常态之前，至少在可预见的周期内，卡片背后依然需要承担最终法律与经济责任的人类所有者，以及为这组 Agent 设定初始目标、风险上限与止损开关的治理者。
