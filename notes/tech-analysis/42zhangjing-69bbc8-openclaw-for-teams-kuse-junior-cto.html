Kuse.ai与Junior.so联创CTO徐宇豪访谈：从零融资到千万ARR的经验与AI员工的未来形态

本期背景与内容导览

本期由 42 章经曲凯访谈 Kuse.ai 与 Junior.so 联创兼 CTO 徐宇豪。前半段复盘 Kuse：团队从邮件营销、设计 Agent 转向文件与文件夹操作，依据的是用户整理、转换资料的行为与较高留存自述；随后放弃无限画布、把固定任务套餐改为按量计费，并通过减少免费额度、提高最低 plan、改变自然内容获客来筛选高价值客户。千万美金 ARR、创始人累计投入约 100万—200万美元、单日千万自然曝光等均为嘉宾或节目方自述，本期未独立核验。 后半段解释 Junior 为何被称为 OpenClaw for Teams：它不是个人助手，而是嵌入团队工作软件、具有职责与项目、账号身份、企业记忆和权限边界的 AI 员工。Kuse 自身是首个客户，另有少量内测用户。嘉宾描述的现有内部实践包括 Ring 接触项目材料、接收会议记录、在群内推进任务，Azura 用公司邮箱外联并协助生成销售线索表格，Tom 监控数据并在一次错误后补发纠正邮件；硬件参会、整体替换 OpenClaw、开源与客户云部署、2000／5000 美元价格方案等则仍是计划或探索。 访谈的技术主线不是“模型已经无所不能”，而是能力提高后，真正的产品工作转向记忆组织、权限、安全、成本、并发、评测与互联网身份支付。主持人多次提出反例：固定 benchmark 难发现新能力，记忆优势难从外部证明，平台放开 Agent 可能损害自身用户关系，模型幻觉并未消失。嘉宾关于取代3—5年员工、SaaS 转型、2026 年进入7×24数字劳动力时代、新职位会出现等表述，应作为其判断与预测保留，不写成已经验证的行业结果。

徐宇豪先按自述交代经历：16 岁进入浙大，之后到 CMU 读硕士，曾在 Facebook／Meta 的 Stories 项目工作，也在 SmartNews 做 AI 与审核相关事务；2023 年开始尝试小项目，2024 年与合伙人创立 Kuse AI。他称 Kuse 2.0 于 2025 年 10 月发布，目前约有千万美金 ARR。这些履历、收入及“Stories 后来成为 Facebook DAU 和 Revenue 第一的产品线”均为嘉宾自述，本期没有外部审计或独立核验。Kuse 当前是三栏式 AI Workspace：左侧文件夹、中间工作区、右侧可调用文件并带沙盒的 Agent；主要面向海外艺人公司、自雇 Agency 和高级白领，也有小公司把资料迁入后用它承担部分人力工作。

主持人确认其 Bootstrap 状态。嘉宾说资金来自几位创始人，累计约 100 万至 200 万美元，而且不是一开始全部投入；主持人随后口中的“一两万刀”不是嘉宾给出的累计投入口径。团队最早做 Email Marketing AI，随后做无限画布上的设计 Agent，可生成海报、设计和网站。真正改变方向的用户信号不是设计师采用，而是另一批人持续上传文件和资料，做整理与 reformat，把材料转成别的展示形式；嘉宾称这类用户的留存显著高于其他场景，但未给出留存数值。团队由此把文件和文件夹操作作为核心，逐步放弃原先服务设计师的场景。

定价也随之变化。早期 20 美元、100 美元套餐对应固定任务数，在偏 Chatbot 的阶段尚能运作；嘉宾认为 2025 年 6 月产品 Agent 化后，一个任务可能迭代 10、20、30 轮，相同任务扣费无法覆盖差异巨大的消耗，用户也未必感知到公司补贴。他把“固定定价都会亏损巨大”作为强烈经验判断提出，不能据此推导所有 Agent 产品都必然亏损。团队最后同时做两项激进调整：放弃无限画布，改成被其戏称为“AI 网盘”的文件夹入口；收费改为 usage based。两项变化都造成用户数和付费数跳水，说明转型有真实代价，而不是无成本升级。

放弃设计场景还包含时机判断。嘉宾称当时 Sonnet 3.5 尚未发布，模型效果不好，需要大量工程 workflow 补能力；团队离开后不久又看到转录作“Lava2”的新模型及 Claude Sonnet 的 Agent 进展，因此他承认若再坚持一阵，结果可能不同。这里保留的是他对时机的复盘，不是“当时放弃必然错误”。最后，团队又发现同一产品难同时服务 C 端与 B 端：现有 Kuse 用户较容易迁移资料和上下文，企业客户已有固定 workflow 和办公软件，需要产品主动进入原有工作流，因此他们转向不同产品线。主持人进一步追问为何不专注单一人群，嘉宾回答其认知是 Agent 时代垂类较难，除非有合规或法律壁垒；这是他的战略假设，后文还需与“不同人群不同产品”和通用 Agent 路线一起理解。

Bootstrap不依赖外部股权融资，而由创始人投入资金并依靠经营发展。本期嘉宾称 Kuse 的创始人累计投入约 100万—200万美元，不是一开始一次投入。
ARRAnnual Recurring Revenue，年化经常性收入，通常把当前订阅等经常性收入折算为年度口径。它不是已到账现金、利润或累计融资。本期的千万美金 ARR 为嘉宾自述，未披露计算时点、客户构成与审计材料。
Usage-based pricing按实际资源或服务用量计费。本期用于对照固定任务数套餐：Agent 任务的迭代轮数和消耗差异变大后，团队改为按使用量收费；具体 Junior 定价仍在探索，两者不可混为一谈。
Evaluation / BenchmarkBenchmark 是一组可重复比较的任务与指标；evaluation 是更广的评价过程。本期从固定 workflow 测试扩展为 Agent 模拟环境、多轮交互和反向行为检查。它能检验已知标准，但主持人指出它不会自动发现未进入测试集的新能力。

00:09:12–00:16:50建立内部评测框架，捕捉模型迭代带来的新机会

  • 既然认为垂类难做，为什么不做一个足够通用的 Agent，而是为不同人群做不同产品？
  • 你们最终怎样补上 Evaluation 框架？它是不是一套自己的 benchmark？

嘉宾先把分产品线的理由延伸到技术阶段：他们把 2026 年看作“7×24 小时 AI 劳动力”机会，认为此前的数字员工仍是工具或 workflow 包装，新产品要进入劳动力场景。这是立项判断，不是对所有数字员工产品的客观分期。主持人随后把讨论拉回一个更具体的坑：产品形态与模型能力绑定过重，每次模型突破都可能触发重写，而没有好的 Evaluation 时，团队不知道怎样迭代才更合适。

他们的补救是先针对自身业务场景建立自动化测试 pipeline，再逐步发展成由多个 Agent 测试对外 Agent。模型或 Agent runtime 变化后，这套系统会评分；测试对象包括多轮对话、特定环境状态、action 是否合理、回复是否合理，以及是否做了不该做的事。最初接近固定 workflow 的 benchmark，后来更强调模拟环境与反向测试，所以嘉宾更愿意称之为 evaluation Agent。这里没有披露测试集规模、评分者与人类判断的一致性，也没有公开分数，能确认的是嘉宾所述工作方式，而不是评测已经充分可靠。

主持人指出关键反例：老业务测试集擅长回归，却不容易发现从未进入测试集的新能力。嘉宾承认这一点要靠技术 leader 的 taste，并补充产品 taste 也必要。他所谓技术 taste，不是单纯追踪模型榜单，而是一线人员在自身 Agent 框架里试用新模型，识别它突然能完成什么任务。公司让技术、产品、设计、销售人员都成为 Agent builder，产品经理和设计师也参与 codebase、指挥多个 Agent；这种直接接触被用来缩短“模型能力变化—新场景假设—产品试验”的距离。发现新能力的责任仍在人，evaluation 不能代替问题发现。

具体例子有两层。第一，团队在 OpenClaw 出现前已做内部 Agent：数据分析 Agent 持续处理新增和变化的数据，再把数据流交给 marketing agents；后者参考 Kuse 的脱敏数据模拟 use case、生成 UGC 视频，经半自动流程分发。嘉宾举例称可定向触达台湾某些奶茶店长，曝光不一定高但画像精准。脱敏边界、投放授权和实际转化均未披露。OpenClaw 这类 runtime 出现后，他们认为许多定制逻辑可收敛为由 skills 学习。第二是一次反向教训：团队在 Anthropic 发布 skills 方法后的第二天就把能力做进 Kuse，却判断客户难理解，因而只开放 templates，每个 template 背后实际是一个 skill；三个月后客户主动问为何还不支持 skills，他们才发现把技术概念藏起来反而错过需求与营销窗口。两件事分别说明一线试验的价值和“替用户预先降低理解能力”的风险。

00:16:50–00:21:07AI员工比人类更贵但更高效：内部Agent实践与对SaaS未来的冲击

  • 公司有多少全职员工和长期运行的 Agent？这些 Agent 的 Token 成本是多少？
  • 既然平均成本不低，为什么仍选 Agent 而不是人？
  • 为什么不把其他人类员工都换成 Agent？
  • 销售 Agent 自建 CRM 的具体过程是什么，为什么它改变了你对 SaaS 的看法？

嘉宾称公司全球约有 15 名全职员工，长期运行的 Agent 有三到四个，覆盖研发、营销、数据和销售；四个 Agent 每月合计 Token 成本超过 2 万美元。主持人据此粗算平均每个每月约三四万元人民币，并指出可以招到不错的人。这不是四个 Agent 各自相同成本的披露，也没有包含全部人类成本或 Agent 基础设施成本。嘉宾仍选择 Agent 的理由是降低人与人之间的沟通摩擦和组织复杂度，而不是单纯工资更便宜。他称公司从上年 12 月起很久未扩张，新招聘需求要先回答为何不能由 Agent 承担；“未来公司会缩小”则是其组织预测。

销售 Agent Azura 的 CRM 案例用于说明这种组织收益从哪里来。嘉宾称 Azura 掌握 Kuse 的客户和销售数据，一位从未写代码的销售与它聊了一晚，形成内部使用的 CRM，界面只是飞书表格。它围绕公司当下的 upsell 工作持续扫描销售数据，寻找可让现有客户体验更多功能或购买更多席位的机会。嘉宾称表格中几乎每条机会价值上万美元，这里应理解为他对潜在销售线索价值的估计，不能直接记成已成交收入、已实现利润或可复用 ROI。

他认为真正的差异不是“AI 会写 CRM 代码”，而是 Agent 已经拥有业务上下文，能把销售需求、数据理解与工具生成连在一起。通用 coding 工具或外采 CRM 也能生成系统，却未必知道本公司此时该筛哪类增销机会。嘉宾用一组反事实估算作对比：内部产品、技术、销售可能先花一个月对需求，再花两个月开发，沟通过程还可能误解；外包仅理解几十万用户数据就可能耗费很久。这些月数是嘉宾用于说明协作成本的主观估计，不是同题对照实验。

这一经历使他从不太认同“SaaS 会完蛋”，转向认为许多 SaaS 可能被迫转型：掌握企业记忆的 Agent 可以生成高度定制的内部软件，减少需求转述和通用产品适配成本。不过，案例只证明嘉宾团队内部做出了一张有业务针对性的表及线索流程，并未证明软件长期维护、权限、数据质量、故障责任和跨企业复制都已解决，更不足以推出整个 SaaS 行业必然消亡。

00:21:09–00:24:24零融资倒逼增长策略：从追求虚假繁荣到聚焦高价值用户

  • Bootstrap、花自己的钱，会让你们在市场推广上的心态不同吗？
  • 你们是用 AI 素材加定向投放获得曝光吗？
  • 转录中的“编辑成本”是什么意思？这是所有 AI 产品的问题吗？
  • 总结做到千万 ARR 的核心，是 go-to-market 体系与曝光量吗？

嘉宾称团队几乎不做高预算广告投放，既因为花的是创始人的钱，也因为 Agent 产品本身服务成本高。他们曾在出海市场获得单日约 1000 万 impression，但主持人询问是否为定向投放时，他明确纠正：做的全是 UGC organic content，不是付费投放。团队围绕学生教育场景制作痛点 use case，自述一度接近“三个帖子就有一个爆火”。因此，这个案例能说明自然内容传播的曝光能力，不能说明付费 CAC 或投放ROI。

高曝光没有自动变成好生意。转录在此处写作“编辑成本”，嘉宾随后用 margin 解释，上下文指向 AI 服务每位用户时存在非零变动成本，而非传统 SaaS 近零成本地让人试用；本文不把这个转录词擅改成某个专业名词。大量学生与免费用户消耗服务，却呈现低转化率或低 LTV，团队遂把此前沉迷的注册量和 impression 称为“虚假”。嘉宾没有提供 LTV、获客成本、毛利率或分群留存的具体数字，因此不能补写 LTV 与 CAC 的精确不等式。

他们的调整有三部分：大幅降低免费额度；把最低付费 plan 从 16.9 美元提高到 39.9 美元，原文没有明确价格周期；改变社媒 use case 和渠道，主动降低对学生等低付费群体的吸引。学生用户并未消失，只是占比逐渐降低。主持人把这一逻辑总结为“定价本身也是一种用户选择”，嘉宾认可，并补充他们有意识地放弃了许多客户群体。这里应与前面的“Agent 时代垂类难做”并读：他们不是无限缩窄场景，而是在通用技术能力与可付费客群之间重新筛选。
