Meta-Harness：让 Agent 学会优化自己的运行方式

一个任务做不好，可能是模型不会，也可能是工具、上下文和验证流程没有把已有能力发挥出来。Meta-Harness 研究让另一个 Agent 读取执行证据、修改这些运行机制，再验证修改是否有效。这里选四篇代表作，逐篇追踪它们看到了什么、改了什么，以及经验怎样进入下一轮优化。

问题与阅读主线Meta-HarnessRHOCIGRSIFlow厂商实践社区讨论研究判断怎样验证迁移资料入口

先把问题落到一次真实的失败上

设想一个修代码的 Agent：它找到问题、写出修复，却因为不知道 Go 安装在哪里而放弃测试；另一次，它测试通过，却把缓存文件一起塞进补丁，导致补丁无法应用。任务都失败了，但这两种失败提供的信息比一个“0 分”多得多：模型可能已经会修这个 bug，缺的是发现工具链、验证和打包交付的执行方法。

这里的 Harness 是模型外部、可复用的运行程序：怎样构造上下文、检索哪些记忆、开放哪些工具、什么时候重试、何时验证与结束。Task-Agent 使用它完成任务；Meta-Agent / proposer 负责读失败轨迹并提出修改；evaluator 执行候选版本、记录任务结果。一个高层 Agent 仅仅分派子任务，还没有完成 Harness 优化；修改必须进入后续任务使用的运行版本。

在一个目标 benchmark 上，外层循环可以这样工作：运行旧版本 → 读取具体失败 → 修改一个运行机制 → 重跑开发任务 → 按结果留下或拒绝候选。迁移到下一个 benchmark 则多了一层问题：旧经验中哪些是通用的执行规律，哪些只是某个环境的路径、字段名或评分习惯？

四篇工作分别推进了哪一步

Meta-Harness 研究优化器如何读取大量原始历史；RHO 研究没有外部正确答案时怎样产生选择信号；CIG 研究怎样保存并修订实验解释；RSIFlow 进一步让优化器积累“何时该改哪一层”的经验。前三篇主要优化任务 Harness，第四篇把 Meta-Agent 自己的运行机制也纳入更新。

选择依据是与这个问题的直接相关性、方法覆盖和可核查材料。Meta-Harness 有明确的公开传播与社区实现；RHO 提供了可用于真实项目的回顾优化入口；CIG 和 RSIFlow 则分别把实验记忆与优化器进化讲得更具体。它们并非经过跨平台统计得到的“热度前四”。

读方法时，始终分清两个循环

任务循环

当前 Harness → 模型行动 → 工具反馈 → 当前任务结果

一次任务内多想、重试或修答案，主要改变本次执行。

优化循环

多次任务的轨迹 → 诊断与候选修改 → 评估 → 新 Harness

输出是一套后续任务也会使用的运行机制。

接下来的四节按“问题 → 输入与可修改对象 → 优化过程 → 实际改动 → 实验证据”展开。具体例子来自论文时注明出处；帮助理解的简化例子单独标明。

1. Meta-Harness：让优化器自己查代码和原始轨迹

Meta-Harness: End-to-End Optimization of Model Harnesses · 作者项目与演示

它要解决的困难：分数说明失败，却没有保存失败如何发生

一次检索策略改动，可能在很久以后才影响答案；一次结束条件改动，可能让已经完成的任务陷入反复检查。如果优化器只看到“候选 A 为 60 分、候选 B 为 55 分”，它不知道是哪一步造成差异。把整段历史先压成固定摘要，也可能提前丢掉真正有用的细节。

Meta-Harness 的核心设计是把每个候选的源代码、分数和原始执行轨迹放进可查询的文件系统。proposer 是能读文件、搜索、比较和修改程序的 coding agent。它自行决定读哪个版本、哪道题、哪一步工具调用。论文中的 proposer 使用 Claude Code / Opus 4.6，任务模型保持冻结；候选通常是单文件 Python Harness，可改提示构造、检索、记忆和编排逻辑。

这里有两层不同的记忆。外层保存的是“哪个 Harness 版本在什么题上怎样运行”，供优化器比较程序；内层保存的是“任务模型这次能用哪些信息”，例如分类时积累的带标签示例。优化器修改内层的存取程序，而外层实验档案继续增长。把新 Harness 搬到另一个任务时，复用的是程序策略，不意味着旧任务的全部示例和日志也进入新任务的上下文。

外层到底怎样运行

  1. 留下完整候选档案。种子 Harness 先运行 search set，即搜索期间可以反复评估、用于指导修改的开发任务。每个候选都有可定位的代码、任务分数、模型输入输出和状态变化。
  2. 由 proposer 自主取证。它可以读任意旧候选，比较成功与失败。系统维护候选集合；同时考虑准确率和上下文成本时，保留 Pareto 前沿，即没有其他候选在两项上都不差、且至少一项更好的版本。系统不硬性规定必须选哪个父代。
  3. 提出可执行的新版本。修改可以小到新增环境信息，也可以大到重写检索流程。轻量检查先排除不能运行的代码。
  4. 外部程序评估并写回结果。评测结果成为下一轮档案。达到预设预算后，按搜索表现选候选，再做最终测试；TerminalBench 实验的切分例外见下文。

注意，评估一个候选、保存它的证据、选择最终部署版本，是三件事。坏候选也会留下代码和轨迹，供后续诊断；当前最好版本可以不变。下一轮 proposer 也可以组合多个旧版本的思路，所以这不是“每轮接受新版本，分数必然单调上涨”的过程。具体改法由 coding agent 根据可见材料推理生成，论文没有另行训练一个专用的修改策略网络。

所谓“一次评估可留下约一千万 token 的诊断材料”，指的是可访问的档案规模，不是每轮把一千万 token 塞进模型。TerminalBench 日志中，proposer 每轮读取文件数的中位数为 82，说明它确实在跨版本取证。

简化示例：银行客服请求“ATM 没吐钞，但账户扣款了”，第一轮误判为“银行卡支付问题”。第二轮既取该标签的相似例子，也取其他标签中的相似例子，可能把“现金未取到但已扣款”这一对照送到模型眼前。关键是检索条件多了当前预测，因此挑战样例直接针对这次判断。这里的请求为本文自拟；程序中的 5／5／5 检索与两次模型调用来自原文。

这只是低上下文成本的一个前沿点。主表采用的高准确率版本是另一种设计：先列完整标签空间，每个标签提供与当前问题相关的代表例子，再给局部异类对照。不能把两个版本的机制与最优数字拼成同一个算法。

编码实验的关键发现：先试错，再改成启动时注入环境

TerminalBench 搜索更能展示“读历史”究竟有什么用。前两轮把结构修复和新的清理／验证提示一起改，分数都下降。proposer 发现二者共享提示改动，于是撤回提示，只测结构修复；退化变小，但仍没有超过基线。后续改完成标记、检查循环等方案也继续失败。

到第七轮，它转向在 Agent 启动前读取工作目录、文件、编程语言及版本、包管理器和可用内存，并注入初始上下文。这项修改避免触碰此前反复退化的结束逻辑。原文实现约增加 80 行，探测有 15 秒超时和失败回退；作者分析其作用是省去初始 2–4 轮环境摸索，尤其帮助依赖专门工具的任务。附录这条单次搜索轨迹和主表最终成绩属于不同报告层级。

实验支持了什么

分类搜索使用三类数据集，20 轮、每轮两个候选。最终所选 Harness 平均准确率为 48.6%，相对 ACE 高 7.7 个百分点，上下文为 11.4K token，ACE 为 50.8K；九个未见分类数据集上的均值为 73.1% 对 70.2%。接口消融中，完整轨迹条件的候选准确率中位数为 50.0，只给分数为 34.6，给分数与摘要为 34.9。这是论文对“原始诊断材料有价值”最直接的控制实验。

数学实验则自动搜出按组合、几何、数论等分路的 BM25 检索程序，在五个评测模型上相对无检索平均提高 4.7 点，其中四个模型未参加搜索。它支持检索策略跨模型复用。TerminalBench 的主表报告 Opus 4.6 上 76.4%、Haiku 4.5 上 37.6%，但搜索与最终评估使用同一 89 题 benchmark。作者检查了题目字符串泄漏；这仍不能替代未见任务上的评测，也不能把当时榜单位置当作持续有效的排名。

这篇工作的可迁移思想

把优化器当作会查案的程序员：保存可追溯的原始证据，让它按需要调阅，再通过执行检验修改。已发现的 Harness 能有跨数据或跨模型收益；优化器本身是否因经历旧任务而更快学会新任务，还需要单独测试。

2. RHO：没有正确答案，也能从过去的执行中提出修改

Evolving Agents in the Dark: Retrospective Harness Optimization via Self-Preference · 项目与使用入口 · Findings of EMNLP 2026

它推进的是反馈来源

Meta-Harness 搜索需要能够为候选打分的开发任务。在真实部署中，用户请求往往没有标准答案，但 Agent 已留下大量工具结果、报错、测试和最终回复。RHO 问的是：能否只用这些过去的轨迹改进未来任务的 Harness？

输入是旧任务及其轨迹，可改对象是一个工作目录里的指令、skills 和可执行工具。实验使用 Codex / GPT-5.5，优化阶段不调用 benchmark 的正确性 grader；最终效果仍由独立的留出任务和 grader 测量。“无标签”并不意味着没有环境证据：编译错误、工具返回值和执行是否提前终止，本来就在轨迹里。

执行、诊断、修改和比较可以由同一个底座模型的不同调用承担，靠各次调用拿到的工作区和输入区分职责。执行时读取当前 Harness；修改时拿到一份可写副本；最终候选是副本中留下的实际文件，而不是模型回复里一句“建议增加检查”。因此这里的学习写回发生在文件和程序中，不需要更新 GPT-5.5 的参数。

完整流程：选问题、重跑比较、生成候选、比较新旧

  1. 挑 10 个困难且不同的问题。模型为历史轨迹估计难度并描述失败类型；将描述编码成向量，用相似性判断哪些问题重复，再以 DPP（行列式点过程）兼顾难度和多样性。直观上，十个相同的构建错误不如“构建、工具误用、提前结束”等不同问题有诊断价值。
  2. 每题重跑 3 次。固定旧 Harness，多次执行，获得同题的不同路径。重跑用于暴露行为差异，因而要求环境能够重置。
  3. 分两种角度诊断。self-validation 对照任务要求和环境观察，找单条轨迹内的错误假设、工具错误与过早结束；self-consistency 比较多条轨迹，找计划、行动或答案上的实质冲突。二者合成修改指令。
  4. 并行生成 3 个 Harness 候选。每个候选都重跑这 10 题；模型逐题比较候选轨迹与固定的旧版参照轨迹，给出 −10 到 10 的偏好分，再取均值。
  5. 有正偏好才替换。选择平均偏好最高的候选，只有严格高于零才接受；相同文件、运行失败或没有正收益时保留旧版。

例如，某个候选在 10 题上的净偏好总和为 12，均值就是 1.2，可以通过正偏好门槛；总和为零则保留旧版。这是本文自拟的计算例子，说明门槛检查的是自评偏好，不是已知真实准确率。

三条旧轨迹的组内比较负责诊断；最终候选选择用的是新旧成对偏好。它没有直接把三个答案多数投票当成真值，也没有因为某个答案最常见就自动认为正确。

轨迹里的证据，怎样变成一条修改指令

下面是按论文诊断接口构造的简化演示，不是作者新增实测：同一个仓库任务重跑三次。A 在默认路径找不到 Go，就停止测试；B 找到另一处 Go 安装位置，运行测试并留下通过结果；C 修改后直接宣布完成，没有运行测试。单条自检会指出 A 的环境假设、C 的缺少验证；跨轨迹比较则会发现 B 的路径和验证过程提供了可复查的替代做法。

诊断因此可以形成一条具体指令：“先检查可用工具链位置，再构建与测试；缺少默认命令不能直接解释为无法验证。”修改调用据此生成工具或操作步骤，新候选再重跑任务，检查它是否真的执行这些步骤。若三次都没有覆盖某个语义错误，这套方法仍可能共同漏判；多次执行提供的是可比较的差异，最终正确性仍要在留出评测上验收。

实际产物：把工具链和补丁卫生变成可调用的检查

原文 §5.2 中，历史 SWE 轨迹暴露出 Go 工具链不在默认 PATH、Python 缓存混入最终 diff 等反复出现的问题。优化后生成的 check_build_and_lint 工具负责定位非标准工具链，并提示哪些生成文件应排除在补丁外。这个修改把“以后记得检查”变成了后续任务能执行的过程。

为什么它可能让新题受益

新的仓库 bug 不需要与旧 bug 相同。只要同样存在“工具链不可见”或“生成文件污染补丁”，检查工具就可能排除一类执行失败。真正可复用的是定位与检查程序；某个 benchmark 的固定安装路径仍可能只在该环境有效。

论文还有一个有用的反例：TerminalBench 中新增的脚本实际上没有被执行，收益主要来自写入指令的操作 playbook。这说明“生成了一个工具”不足以解释提升，还要检查后续运行是否调用它、在哪一步改变了行为。

结果与自评的误差

单轮回顾后，作者报告 SWE-Bench Pro 留出集通过率 59% → 78%，TerminalBench-2 为 71% → 76%，GAIA-2 为 29% → 37%。按其数据划分，SWE 和 GAIA 留出集各为 100 题，TerminalBench 为 59 题；这些数字不等同于各 benchmark 官方全量成绩。

自偏好没有完美识别最好的候选：SWE 实验中，被选版本为 78%，另一个较低偏好版本最终达到 85%。原始轨迹直接交给同样可改工具、skills、指令的 proposer，只得到约 60%，低于完整 RHO 的 78%；这支持结构化回顾有额外价值，但不能保证自偏好在其他环境总能选对。

这篇工作的可迁移思想

一个模型从头完成任务困难时，仍可能利用环境结果和多条执行之间的差异识别部分错误。RHO 把这种诊断能力接到持久 Harness 修改上。作者只验证单轮、单一底座／框架，并为各 benchmark 分别生成 Harness；长期多轮增益和跨 benchmark 迁移仍待验证。

3. CIG：让失败修改也能改变下一次实验

Causal Improvement Graph for Agentic Harness Optimization · 2026 年 10 月预印本

它要解决的困难：历史还在，当前解释却容易丢失

保留所有日志以后，优化器每轮仍要重新想起：上一次为什么试这个改动？哪个解释已经被否定？分数提高，究竟支持了假设的哪一部分？CIG 把这些实验关系变成持久状态。它保存四类节点：Evidence 记观察，Hypothesis 记可检验解释，Intervention 记可执行修改，Outcome 记测得结果，并连接来源、支持、反驳和版本关系。

它仍然修改任务 Harness，并使用外部评价。变化主要在外层：proposer 被用于局部的观察、提案和实现操作；图维护当前知识状态，供下一轮规划读取。作者将“causal”明确限定为由干预和结果驱动的改进推理，没有声称完成严格的因果识别。

先看论文里的一个失败实验

附录 A.9 从“把所有示例都放入上下文”改为“只取与问题相似的示例”。整体分数上升，但 LawBench 从 60 降到 46。这个结果引出假设：局部检索减少了无关示例，也可能删掉法律分类需要的标签与模式覆盖。

Evidence · 观察

检索提高了整体成绩，却让 LawBench 60 → 46。

Hypothesis · 预测

补回覆盖应该恢复法律分类，同时保住其他任务的收益。

Intervention · 修改

60% 提示预算放最近邻，剩余位置按答案空间与词元覆盖补充示例。

Outcome · 实测

LawBench 46 → 52，但 USPTO 40 → 33.33；整体 58 → 57.78。

这个干预没有达到联合目标：它恢复了一部分法律分数，却把化学任务改坏。图因此保存“这项联合改进预测失败”的判断，同时保留“法律任务出现局部恢复”的事实。下一轮不能把它压成一句“覆盖有用”，也不能简单删除这个失败候选。原始观测、已失败的预测和仍未解决的解释各有自己的位置。

具体来说，先读图与必要的原始历史，提出“假设—干预”计划，明确父代、要保留的机制和预期效果。另一次 proposer 调用按证据、预期收益、信息价值、新颖性、可证伪性、成本和风险七项 0–4 分评估计划，并考虑候选之间的重复。这些是模型给出的计划判断，不是任务执行后测得的奖励。只有实现并交给外部 evaluator 运行后，才得到真实候选成绩及修好、改坏、未变的任务记录；Update 再据此修订假设。

附录还给出一个不同搜索中的状态干预：从同样的新结果和历史出发，一条分支保留“继续精修局部相关性”的旧解释，另一条分支更新为“局部检索可能丢了广覆盖”。前者继续扩检索池和重排，均分留在 57.33；后者增加全局标签／模式锚点，达到 60.44。这个单次对照说明改变历史的解释，可以改变下一步实验；它与上一段 57.78 的失败案例是两条独立轨迹。

证据有多强

在作者匹配的三类 Agent 任务比较中，CIG 的留出集宏平均为 44.6%，其自行实现、可访问完整历史的对照为 40.1%，均报告三次运行均值。另有控制实验逐步加入类型记录、关系、跨轮修订和基于图的选计划，并测试打乱关系、只追加不修订等变体，结果支持这些结构在该协议中的贡献。

但同等“候选评估次数”不自动等于相同 token 与墙钟成本；图上的归因判断也仍由模型作出。论文主要研究单次搜索内部的持续状态，没有验证把整张改进图带到陌生任务族后能否更快适配。

这篇工作的可迁移思想

优化器需要保存的不只是“哪些版本分高”，还有“当前相信哪个解释、依据是什么、什么结果会使它改判”。失败能留下信息增益，即使该候选不被部署。这使它比普通成功经验库更接近一个可修订的实验记录系统。

4. RSIFlow：优化器自己也要学习该改哪一层

RSIFlow: Adaptive Self-Improvement Workflows with an Evolving Meta-Agent · v2，2026-11-02 · 代码

先解释它比“自动调 Harness”多做了什么

对同一条“代码没有通过”的反馈，有三种不同干预：修当前程序中的一个边界条件；改 Harness，使所有后续任务都检查交付格式；训练模型，改善反复出现的语义能力缺口。单纯扩大可写范围没有回答应该选哪一种。RSIFlow 让 Meta-Agent 根据轨迹和反馈选择 Artifacts、Harness 或 Model 更新，并把选择和执行的结果写回 Meta-Agent 自己的 Harness。

其中 Artifacts 指当前任务的程序或答案；Harness 指跨任务复用的执行方法；Model 指任务模型权重。Meta-Agent 的基础模型权重保持固定，其进化发生在自己的技能库、行动接口及调用指令中。论文的任务模型为 Qwen3-4B／8B，主实验跑五轮，每轮最多两次候选尝试。

一次更新怎样变成“优化经验”

  1. 定位错误属于哪一层。结合当前任务要求、出错阶段、已有检查和历史技能，选择更新路线；保留另外两类任务组件。
  2. 实施并比较候选。Harness 路线改 Action／Skill／Planning 机制；Model 默认用成功轨迹做 SFT；Artifacts 路线指导 Task-Agent 修改自己的当前产物。训练阶段在相同父代、相同任务批次上比较，首个合法且有正收益的候选被接受。
  3. 对齐新旧轨迹中的关键事件。比较相同子目标、工具调用和错误位置，区分哪些任务修好了、哪些退化了，保留全任务评价。
  4. 形成有条件的技能。记录适用条件、修改对象、具体操作、必须保留的行为、预期响应，以及支持和反对证据；通过新增、补证、修订或合并维护。
  5. 接入下一轮决策。更新检索与行动接口、执行指令，让技能进入之后的诊断、路线选择和候选构造。仅存下一段总结，还没有完成这一步。

原文五轮案例：为什么先改 Harness，后来改模型

附录 C.3 的一条实际轨迹是 Harness → Harness → Model → Model → Artifacts。第一轮发现交付格式问题：需要源代码时，Agent 可能返回解释或执行输出，因此加入完整源代码的交付检查。第二轮将“交付要有证据”的判断用于工具任务，新增基于实际执行回执的完成检查，防止只在文本里声称操作成功。这里的回执是工具或环境返回的执行证据，区别于 Agent 自己的完成声明。

检查格式和回执后，仍有语义错误，于是第三、四轮转到模型更新：先用 3,798 次符合要求的成功调用做 LoRA replay，再扩展到 5,397 次；第二次应用给已有 replay 技能补充证据。第五轮针对当前输出的局部缺陷，指导 Task-Agent 在预算内修改、测试并重新提交，保持模型与任务 Harness 固定。

这条案例的报告均分依次为 32.23 → 38.04 → 45.46 → 47.11 → 51.21。第一项已经是第一轮干预后的分数，不能把它当原始基座。第五轮的训练产物也不会直接搬到测试题：报告阶段使用冻结的修复指导，对新题生成的产物最多追加一次允许反馈下的修订。

技能到底写了什么：从“记住错误”到条件化操作

以原文交付检查技能为例

触发：任务要求源代码，却提交了解释或运行输出。动作：在提交路径加入完整源代码检查。保留：现有任务接口与有效解题行为。预期：减少格式不合约的失败。边界：源代码格式正确，不代表算法正确；语义错误应继续诊断，不能无限添加格式检查。

这些字段使技能既能支持行动，也能限制错误推广。后续工具任务可以复用“完成声明必须对应证据”的原则，但具体实现换成检查环境回执。跨任务保留的是有适用范围的优化程序；当前题修好的答案仍属于当前题。

存下的技能，怎样进入下一轮选择

附录 D.1 把检索实现写得很具体：将当前任务、错误和执行阶段组成查询，与技能文本做词项匹配，普通匹配词贡献 1 分，错误词匹配额外加 3 分，即共 4 分。检索只负责找候选经验；Meta-Agent 还要对照轨迹检查技能的适用条件，再把选中的经验放进诊断和修改指令。路线选择依靠带检索经验的模型推理，没有另外训练一个三分类路由器。

例如，某次输出又是解释文字而非要求的源代码，交付检查技能会提示 Meta-Agent 检查提交环节，并据此生成 Harness 修改。若已经提交完整源代码、错误发生在算法逻辑，词项匹配即使找到了这项技能，其适用条件也不满足；Meta-Agent 应继续判断能否局部修输出，或是否有反复出现且有合格训练数据的能力缺口。这段是对原文技能调用方式的演示，不是对路由正确率的额外实验结果。

接受修改仍然依靠运行结果，检索分不表示预期收益。自拟算例：同批 20 题中，候选修好 4 题、改坏 2 题，其他不变，则净通过率提高为（4−2）／20＝10 个百分点，满足正收益条件。它说明这道门槛判断的是整批净增益，不能从“接受”推断每道旧题都没有退化；实际协议还要检查候选合法性与需要保留的约束。

它证明了优化器在进化吗

六个 benchmark 覆盖代码、工具使用、多跳问答；两种底座共 12 个组合，作者报告 11 个超过最强对照。4B 消融中，完整系统三域平均约 51.21，关闭 Meta-Agent 进化约 45.47，相差 5.74 个百分点。另一个更贴近优化能力的比较，让不同 Meta 版本都修改同一个初始 Task-Agent，而非继承越来越强的任务模型；较晚 Meta 版本在代码和问答上的收益更大，但工具使用并不单调提高。

这些是“积累优化经验有用”的证据。其范围仍是训练过的三个领域：报告阶段模型、Task-Harness、Meta-Harness 与技能库冻结，不能把结果解释为测试时不断跨题自学。总演化成本也不因相同单题预算而自动相等。面对全新任务族是否能以更少预算学会优化，论文尚未给出充分检验。

这篇工作最接近的问题

一次改进会改变下一轮的瓶颈，所以 Meta-Agent 要积累“这个症状在什么条件下适合改 Harness、训练模型或只修当前输出”的经验。它明确实现了优化过程的经验写回；可泛化到多远、是否持续加速，仍应作为研究问题。

厂商已经怎样把这件事做进工作流

公开材料中最接近论文外层循环的是 LangChain 的 Better Harness 和 OpenAI 的 Agent Improvement Loop。Anthropic 的案例更侧重人工根据运行结果设计、删减 Harness；Qoder 将项目中的重复摩擦转成审查与持久配置。它们自动化的范围各不相同。

LangChain：用真实失败构造 eval，再自动诊断与定向修改

Better Harness 从人工案例、生产 traces 和外部数据中整理 eval，按工具选择、多步检索等行为打标签，分成 Optimization 与 Holdout 两组。先跑基线，再让循环读轨迹、提出定向修改、检查新增通过与旧题回归，最后人工审阅指标没有覆盖的问题。其“一次一个定向变化”允许同时改提示与工具，只要围绕同一个执行机制。

一个具体例子是 search-then-email：Agent 反复发出近似搜索而迟迟不交付。优化指令要求信息足够后停止重复搜索，并改善新工具的说明与组合方式。另一个例子是用户已提供时间和约束，Agent 却继续追问；修改要求复用已给条件和合理默认值。这些都是能从 trace 中定位、能在后续 eval 验收的行为变化。

在另一个Deep Agents 案例中，作者固定 GPT-5.2-Codex，报告 TerminalBench-2 从 52.8% 提高到 66.5%。实际修改包括结束前自验证、启动时注入环境、检测重复编辑，以及规划／执行／验证阶段的推理预算分配。这个多项工程迭代结果不等同于把全部提升归因给单一自动优化算法。

与论文的连接：它把 Meta-Harness 的“从轨迹提案”接到生产数据、留出测试和发布审阅上。最值得借鉴的持久资产包括带行为标签的 eval、候选差异和逐题回归，优化器只是其中一个环节。

OpenAI：把运行反馈写成可实施的修改交接

Agent Improvement Loop 是一个 Cookbook 示例：在合成公司材料上运行分析 Agent，收集五条真实生成轨迹，加入示例人工反馈和模型反馈，将要求转成 Promptfoo eval，再交由 HALO（Hierarchical Agent Loop Optimization）分析当前 Harness、轨迹和评价，排序下一轮修改并形成 Codex 实施交接。

例如，Agent 可能把管理层的 NRR 估计当成正式指标。示例把“缺乏财务确认时不能报告正式 NRR”固化为评测要求。HALO 不只改提示措辞，还建议确定性事实账本、对实际交付文件做校验，以及保留生成的回归题。

这个 notebook 的评测门检查的是现有轨迹输出；验证改后版本需要换成真正运行候选 Agent 的 provider 并重新评估。它给出了反馈到实施的衔接，自动实现、合并和部署是可继续连接的工作流，不能将这个示例当作已经验证的无人值守产品闭环。

Anthropic：先校准评价器，再随模型变化删掉失效脚手架

长程应用开发实验由 planner 扩展需求，generator 编写应用，evaluator 用 Playwright 实际操作、检查功能并反馈。作者先将审美和质量要求变成标准，再读 evaluator 日志，用人工判断校准它过于宽松的评价。这里循环内主要改的是应用产物；外层 Harness 的设计与评价器校准仍主要由研究者推动。

随着模型升级，作者逐项尝试移除旧结构：较新模型不再需要早期的 context reset，后来又移除 sprint 划分，把 evaluator 移至构建末尾。这个观察提醒 Meta-Agent：候选操作应包括删除或降低检查频率。对较弱模型有效的复杂工作流，换模型后可能成为延迟与 token 成本。

Qoder：把反复提醒变成项目级规则、技能或检查

Qoder Better Harness 是工程审查插件，检查项目指引是否容易发现、验证步骤是否可执行，以及哪些环节反复需要人工提醒。官方示例是分析“发布前为何总漏掉链接验证”，先给证据和建议，再选择一项有明确验收标准的改进，例如补规则或把验证做成脚本，并在后续任务验证。

它与 RHO 都关注真实项目的历史摩擦；公开文档描述的是带人工选择的审查与改进入口，没有给出 RHO 式多次重跑和自偏好淘汰协议。相同的 Better Harness 名称，也不代表与 LangChain 使用同一个实现。

社区为什么讨论它，又在质疑什么

Lior Alexander 对 Meta-Harness 的介绍帖在本次可读取页面上显示约 4.39 万浏览、251 赞、33 次转帖、393 次收藏。帖子引用作者发布信息，突出代码／日志／分数的文件系统与多任务结果。这个快照足以说明 Meta-Harness 有可见传播，不能据此推断四篇论文的相对热度。

传播时最容易压缩掉两处条件：“同模型可有六倍性能差距”是论文引言引用的背景观察，并非 Meta-Harness 自身的统一六倍增益；“一千万 token”是可访问原始材料的规模，并非单步实际上下文。评论提出的实际问题包括回归怎样评估、规则放入上下文后是否真的被执行。后二者也正是研究应测的行为环节。

HN 与 Reddit：可运行演示和真实能力提升之间有距离

HN 的 Simple Meta-Harness 讨论在读取时为 51 points。支持者认可完整轨迹便于定位问题；质疑集中于演示任务过于简单、术语先于解释、成本，以及自修改失败后怎么恢复。帖中一位独立实现者明确说，自己的试验只证明修补不良 prompt 的纪律改善，没有证明任务 Agent 能力提升。这些评论针对社区 demo，不能直接替代对论文实验的评价。

Reddit 的相关 skill 帖也将例子标为 synthetic demo，并讨论冻结／缓存输出可能导致不真实的优化信号。可操作的启发是：评估必须重新运行被修改的执行路径，观察真实行动和结果；只重评缓存答案，不能验证 Harness 改动。

小红书：目前不能据公开样本做热度结论

本次抽样的相关笔记链接未能取得可读正文与稳定互动量，因而不把搜索摘要写成已核查的用户观点，也不给出“国内最热工作”之类排序。小红书官方招聘页提到的 Harness／Agent 进化属于组织需求信息，与小红书社区用户对这几篇研究的讨论度是两件事。

所以社区材料在这里承担两个作用：说明 Meta-Harness 的公开关注点，以及揭示实现者关心的成本、回归与有效评测。CIG 和 RSIFlow 的入选主要来自其机制代表性，尚没有可比的跨平台热度数据支持。

读完四篇，原始设想已经走到了哪里

让专门 Agent 针对目标任务自动改 Harness，已有直接研究和工程实现。Meta-Harness 与 RHO 最贴近这个起点：前者用评测与完整历史搜索，后者用部署轨迹和自偏好回顾。CIG 使经验以可修订的实验关系保留；RSIFlow 再让 Meta-Agent 从改进结果中更新自己的技能和调用方式。

但需要区分三个结果：为每个目标分别调出专用版本；把已发现的运行策略直接搬到相近任务；积累旧任务经验后，以更少反馈为陌生任务发现新策略。分类 OOD、数学跨模型和 RSIFlow 的 Meta 版本比较分别提供了不同方向的证据，尚不能合并成第三个结果已被充分证明。

我的判断：真正可积累的对象，是“有条件的干预经验”

“多验证”“用工具”“更仔细”很难成为有效经验。可操作的经验要包含：观察到什么错误 → 怀疑哪种机制 → 在什么条件下改哪一层 → 哪些行为必须保留 → 预期哪项结果变化 → 实际变化与反例。Meta-Harness 提供原始依据，RHO 提供低标签反馈，CIG 管理解释修订，RSIFlow 把经验用于路线选择。这里是一种综合设计思路，四篇论文没有共同验证这样一套完整系统。

一个更具体的研究问题：选择信号能否可靠区分值得持久化的修改

当环境没有最终真值时，能否利用编译结果、工具状态、同题多次执行和输入输出约束，判断一次修改修复的是通用执行缺陷，还是只让当前轨迹更像“成功”？RHO 的自偏好错过更优候选、CIG 的局部恢复伴随整体退化，都说明诊断信号与最终任务收益之间还有距离。

可以把这个接口单独研究：固定候选生成器，只替换候选选择信号；对照原始自评、成对偏好、可执行约束和跨任务反例检验。先验证哪种信号更能选中在新任务上有效的修改，再讨论是否用于 Harness 搜索或模型训练。这样能把“自动优化有没有收益”拆成候选质量与反馈可靠性两个可测问题。

下面是本文建议的实验协议。任务 Harness 变强和 Meta-Agent 更会优化，应分别测量。

  1. 留出整个任务族。例如用代码修复和工具调用积累优化经验，之后才开放一个陌生的交互任务族；每个族内部另分开发与隐藏测试，避免把随机切分当成跨族迁移。
  2. 固定优化器与任务模型。比较无历史、原始历史、可修订实验记录和条件技能四种状态，提供相同任务接口。先固定模型参数，以隔离 Harness 学习；允许训练权重时另列实验。
  3. 比较整条适配曲线。记录调用数、实际 token、费用与墙钟时间；报告同预算最终分数及达到目标分数的预算。相同候选数可能隐藏不同的取证和诊断成本。
  4. 查旧能力与任务行为。适配新族后重测旧族，并确认新增工具实际被调用、规则改变了哪一步。把每次修复与回归连回候选 diff。
  5. 设置直接搬运对照。将旧 Harness 或旧 skill 直接用于新任务，与继续由 Meta-Agent 进行搜索分开。这样才能区分“好策略可复用”和“学会更快发现新策略”。

一个可检验预测是：原始轨迹档案在证据量小的时候可能已经足够；任务族和失败解释增多以后，可修订记录应降低重复尝试、冲突修改和每次诊断的成本。如果只是记录更漂亮，适配预算与真实通过率没有改善，就不足以支持“优化能力积累”。

Meta-Agent Challenge 可作为可靠性参照：其 39 个配置仅 5 个超过相应人工 scaffold 均值，且报告明显的跨运行方差和 reward-hacking 尝试。它提醒我们重复运行、隐藏任务与完整成本统计都应成为结果的一部分。

领域应用见代码、科学研究与芯片设计专题：进一步解释 Self-HPO、Organon、DrugHarness、Dr. RTL，以及芯片 Harness 双循环原型。

扩展阅读：原有自我改进综述的定义、分类、文献审计与工程边界

下面保留原综述的宽口径分析，包含权重、prompt、记忆、工具与完整程序更新。它为四篇精读提供背景，不承担本页代表工作的方法讲解。

它解决的真实问题：大家说的“自我改进”根本不是同一种东西

当前文献把 self-training、self-reflection、self-play、memory、prompt optimization、自动造工具、修改 Agent 源码乃至递归自改都放在相似叙事中。只看名称，会把三件完全不同的事混在一起：一次任务内利用上下文做得更好；跨任务保留经验；修改产生更新的机制本身。

综述的关键动作是把现代 Agent 拆成“模型核 + 运行 scaffold”。这样，模型微调和外部软件更新不再是两个不相干的领域，而是同一个系统的不同持久化通道。这个视角也解释了为什么近中期最常见的改进并不发生在权重里：prompt、playbook、工具封装、检索规则和代码 diff 更便宜、更透明，也更容易回滚。

定义：先把会话状态与能力状态分开

论文把时刻 \(t\) 的 Agent 写成：

\[ \mathcal{A}_t=(\theta_t,\Sigma_t),\qquad \Sigma_t=(p_t,m_t,\mathcal{T}_t,g_t) \]
\(\theta_t\)基础模型参数。通过 SFT、RL、偏好优化或其他梯度方法更新，通常成本高、影响面广、回滚与归因困难。
\(p_t\)可复用的系统提示、策略模板或工作流说明；不是一次请求里的临时措辞。
\(m_t\)记忆对象、组织结构，以及写入、检索、更新、删除策略。保存原始历史不自动等于有效学习。
\(\mathcal{T}_t\)工具集合及调用接口，包括路由、修复、文档和自动创建的新工具。
\(g_t\)路由、调度、权限、安全约束等控制逻辑；完整 scaffold 自改通常主要发生在这里和代码实现中。
\(X_t\)KV cache、中间计划、当前对话历史等临时执行状态。任务结束后若被丢弃，就不算系统能力的持久更新。

自我改进被进一步拆成“执行产生信号”与“更新提交状态”两步：

\[ \mathcal{A}_{t+1}=\mathcal{U}\!\left(\mathcal{A}_{1:t},\;\mathcal{E}(\pi_{\theta_t,\Sigma_t};\Sigma_t,\mathcal{C}_t)\right) \]

这里 \(\mathcal{E}\) 产生轨迹、批评、偏好、验证结果或候选 patch；\(\mathcal{U}\) 决定是否写回。一个容易忽视的边界是：论文只要求学习信号由 Agent 的执行诱发，并不要求更新器、奖励、任务或验收规则都由 Agent 自己设计。因此它采用的是宽口径的 self-improvement，而不是“完全自治地重写自己的学习算法”。

形式化里最关键的缺口：更新不等于改进

原定义只要 \(\mathcal{U}\) 产生持久变化就进入“self-improvement”框架，却没有要求 \(\mathcal{A}_{t+1}\) 在任何独立目标上优于 \(\mathcal{A}_t\)。写入一条错误 memory、把 prompt 改坏、训练出 reward-hacking policy，同样满足“自诱发 + 持久提交”。因此这个公式严格说定义的是 self-induced adaptation；只有增加验收谓词，才定义了 improvement。

\[ \widetilde{\mathcal A}_{t+1}=\mathcal U(\mathcal A_{1:t},\mathcal E_t),\qquad \mathcal A_{t+1}=\begin{cases} \widetilde{\mathcal A}_{t+1},&\text{if }G(\widetilde{\mathcal A}_{t+1},\mathcal A_t;\Gamma_t)=1\\ \mathcal A_t,&\text{otherwise} \end{cases} \]

这里 \(G\) 是独立的 promotion gate，\(\Gamma_t\) 是版本、权限、隐藏测试、安全策略与回滚记录组成的治理状态。把 \(\Gamma\) 单列出来很重要：如果最终验收器也只是 Agent 可写的 \(g_t\) 一部分，Agent 就能通过降低门槛来制造“进步”。可写的运行 scaffold 与不可由同一闭环任意修改的治理根，应当是不同的信任域。

这组三分法说明“有 feedback loop”远远不够。至少还要问：更新对象是什么、保存到哪个版本、跨过什么边界、由谁验收、失败时是否回滚。同一篇工作甚至会因部署生命周期不同，从普通 test-time compute 变成真正的 scaffold learning。

证据边界：为什么它更像 field map，而不是 systematic review

  1. “239 篇”不是当前材料中可复算的样本量。当前配套清单的方法区有 245 行，另有 1 行 benchmark；按大小写归一后只有 226 个唯一标题、223 个规范化唯一论文 URL。论文源码含 715 条 bibliography entry，正文实际引用 526 个唯一 citation key。差异来自持续更新、跨类重复与错误链接，但论文没有给出 239 到任何公开集合的精确映射。
  2. 缺少系统综述的检索协议。没有说明数据库、检索式、时间窗、双人筛选、纳入排除标准、质量评级或遗漏风险。因此它能说明“作者如何组织领域”，不能支持“领域方法的总体效果是多少”。
  3. 形式化只保证持久适应，没有保证提升。更新算子没有要求 held-out 能力增益、回归上限或风险约束；一个持久的坏更新也满足原公式。论文在评测章节补充了轨迹、迁移与安全要求，但没有把这些条件接回“什么才算 improvement”的定义。
  4. 分类包含规范性判断。例如“权重更新更慢但迁移更广”“scaffold 更快且可回滚”是很好的默认设计启发，不是跨论文统一控制变量后的因果结论。
  5. 系统边界仍有模糊处。Agent 被写成 \((\theta,\Sigma)\)，但环境、critic、数据管线与权限系统被放在上下文或更新器外部。若这些部分也会演化，谁算 Agent、谁有最终写权限会直接改变“自我”的含义。
  6. 很多案例是自动化改进，不是开放式自我决定。任务分布、奖励函数、测试集、模型 API、沙箱和停止条件大多仍由人类规定；“没有逐步人工介入”不等于“系统自己选择了目标和价值函数”。
不要从这篇综述推出

不能推出 recursive self-improvement 已经进入失控加速阶段，不能推出 scaffold 更新必然比权重更新安全，也不能把一次 benchmark 上升解释成通用能力复利。现有证据更接近“有界搜索 + 可验证写回”。

工程落地：一套比“让 Agent 自己学”更具体的协议

  1. 定义可写面。明确 prompt、memory、tool、workflow、model adapter 哪些可改；权限与最终验收器默认不可被同一闭环修改。
  2. 把治理根与运行 scaffold 分域。将身份、权限、隐藏测试、准入阈值和回滚账本置于受保护的 \(\Gamma\)；Agent 可以提交修改建议，但不能直接改写自己的最终验收条件。
  3. 把临时状态与持久状态分开。只有跨任务保留且可版本化的内容进入 improvement ledger；会话内反思不冒充能力积累。
  4. 候选更新在隔离副本运行。先做功能测试、权限测试、成本上限、随机扰动与对抗输入，再进入 canary。
  5. 训练信号与最终裁判分离。使用隐藏回归集、不同 judge 或可执行 oracle；记录 judge 版本与预算。
  6. 同时度量 gain、regression 与 cost。禁止只用最优峰值；报告学习曲线、方差、迁移和每单位资源增益。
  7. 保留 lineage 与一键回滚。每次 commit 都能追溯到经验、diff、验证证据与适用范围，失败更新不能污染后续记忆。
  8. 为 skill 写部署契约。记录前置条件、依赖、权限、适用域、测试与失效方式；检索相似不等于满足调用条件。
  9. 达到稳定门槛后再做权重固化。把成熟的 scaffold 经验蒸馏进参数，但重新跑完整安全与遗忘评测。
